# 전체 흐름 안내

이 문서는 저장소 전체를 처음 보는 사람이 무엇을 만들었고 어떻게 쟀는지를 순서대로 따라갈 수 있게 정리한 안내서다. 개발자, 평가자, 새로 합류한 사람 누구나 README 다음에 읽으면 된다. 낯선 낱말은 [용어집](glossary.md)에 있다.

## 1. 풀려는 문제

상담 중 고객의 말은 계속 바뀐다. 해지를 말하다가 환불로 바뀌고 결제일을 잘못 말했다가 고친다. 그때마다 적용할 약관 조항과 올바른 안내가 달라진다.

흔한 AI 챗봇은 고객이 말할 때마다 큰 AI(생성형 LLM)에게 처음부터 다시 묻는다. 큰 AI는 한 번 답하는 데 몇 초가 걸리고 비싸다. 그래서 판단을 덜 자주 하게 된다. 그 사이 이미 틀린 안내가 화면에 남거나 고객에게 나간다.

## 2. 해결 방향

판단과 생성을 나눈다.

- "고객이 원하는 게 해지인가 환불인가", "이 조항이 지금 필요한가", "지금 확정해 답할 수 있는가" 같은 작은 판단은 **판별 모델**에게 맡긴다. 판별 모델은 문장을 쓰지 않고 정해진 질문에 확률로만 답한다. 빠르고 싸서 고객이 말할 때마다 판단할 수 있다.
- 고객에게 할 말은 **생성형 LLM**이 근거가 충분할 때만 만든다.
- 환불 금액 계산, 날짜 비교, 본인 확인처럼 틀리면 안 되는 일은 **코드와 업무 시스템**이 한다.
- 고객이 말할 때마다 대화에 **버전 번호**를 붙이고 옛 버전으로 하던 작업은 취소하거나 버린다.

이 생각이 맞는지 직접 만들어 보고 숫자로 확인하는 것이 이 프로젝트다.

## 3. 무엇을 만들었나

모두 가상의 회사, 약관, 고객이다. 실제 회사나 개인정보는 쓰지 않았다.

1. **가상 회사와 약관.** 구독 서비스 회사(조직 A, "별담 플러스")의 환불·해지 약관 23개 항목을 썼다. 일반 규정, 예외, 절차, 부칙, 별표가 함께 걸리도록 했다. 가상 고객 16명과 업무 시스템의 호출 규약도 만들었다.
2. **판별 데이터.** 상담의 한 순간(대화와 그때까지 확인된 사실)과 그 순간에 던질 질문, 정답을 묶은 사례 105건(대화 40개)이다. 연습용(train 64), 조정용(val 21), 최종 시험용(test 20)으로 나눴다. test는 나눈 뒤 바꾸지 않는다.
3. **판별 모델 비교.** 같은 데이터로 Jev, Cloudflare Clef·Clef-flash, 생성형 LLM(Gemini), 사람이 짠 규칙을 비교해 Jev를 골랐다([결정 기록 0011](adr/0011-판별-백엔드와-질문-세트.md)).
4. **상담 엔진.** 대화 버전, 조항 검색, 판별, 정책 코드, 응답 생성을 순서대로 처리한다([엔진 설계](engine.md)).
5. **업무 시스템.** 조회, 환불 금액 계산, 접수, 상담사 연결을 하는 모의 서버를 Go로 만들었다(`bizapi/`). 엔진은 금액을 계산하지 않고 이 서버가 준 금액만 안내한다.
6. **AI 고객과 자동 채점.** AI가 시나리오대로 고객을 연기한다. 코드와 다른 AI가 상담 결과를 채점한다(`jikgam/sim/`).
7. **음성.** Pipecat으로 음성 인식(STT)과 음성 합성(TTS)을 엔진에 붙였다([음성 문서](voice.md)).
8. **두 번째 회사.** 약관과 업무 시스템 형식이 다른 조직 B를 설정과 변환 장치(어댑터)만으로 붙였다([조직 B 문서](org-b.md)).
9. **한국어 판별 모델 학습.** 이 PC의 GPU로 공개 모델(Qwen3.5)을 학습시켰다([학습 문서](training.md)).
10. **웹 화면.** 상담 운영팀이 쓰는 고객사 콘솔과 직감 팀이 쓰는 관리 콘솔 두 개다([웹 콘솔 안내](design/README.md)). 화면은 결과 폴더의 로그와 녹음을 읽어 그린다.

## 4. 어떻게 쟀나

결과를 믿을 수 있게 하려고 네 가지 원칙을 지켰다.

- **채점 기준을 먼저 정했다.** 무엇을 어떻게 잴지와 어느 정도면 성공인지를 측정 전에 [평가 기준 문서](evaluation.md)에 적고 저장소에 올렸다. 나중에 정의를 고쳐야 할 때는 지우지 않고 날짜와 이유를 붙여 덧붙였다.
- **조정과 최종 시험을 나눴다.** 모델이나 질문 문구 선택은 조정용 데이터(val)와 개발용 시나리오로만 했다. 최종 판정은 개발 중에 쓰지 않은 데이터로만 했다. 판별은 test, 상담 시나리오는 미공개 평가 시나리오다.
- **설정을 고정하고 한 번만 평가했다.** 최종 평가 직전에 코드, 설정, 데이터의 해시를 결정 기록으로 고정했다([결정 기록 0014](adr/0014-엔진과-평가-설정-고정.md)). 결과가 나빠도 설정을 바꿔 다시 평가하지 않는다.
- **숫자는 다른 사람이 다시 계산했다.** 측정한 쪽과 분리된 검토자가 원본 로그로 모든 수치를 다시 계산해 대조했다.

비교한 상담 방식은 세 가지다. 문서에서는 정책 A·B·C라고 부르고 실행기 옵션(`--policy`)도 같은 글자를 쓴다.

| 실행기 옵션 | 방식 | 확인하려는 것 |
|---|---|---|
| A | 개선형 RAG 챗봇(검색은 엔진과 같음. 판별 모델과 대화 버전 없이 발화마다 생성형 LLM 한 번) | 기준이 되는 흔한 구조 |
| B | 같은 엔진, 판단만 생성형 LLM | 엔진 구조의 효과 |
| C | 같은 엔진, 판단은 판별 모델(Jev) | 빠른 판별의 효과 |

음성 평가에서는 B를 빼고 정책 D를 더해 A·C·D를 비교했다. D는 C에 "실시간 자막으로 미리 판단하고, 말이 끝나면 확정 자막을 기다리지 않고 바로 판단을 이어 가는 것"을 더한 방식이다([결정 기록 0018](adr/0018-음성-정책-D.md)).

## 5. 진행 순서

| 날짜 | 한 일 |
|---|---|
| 2026-10-12 | 설계, 가상 약관과 고객, 판별 데이터 105건, AI 고객 시나리오 30개, 정답 교차 검토, 데이터 분할 고정 |
| 2026-10-14 | 평가 기준 고정 → val로 판별 모델 비교와 질문 문구 실험 → 상담 엔진, 업무 시스템, AI 고객과 채점기 → 개발용 시나리오로 세 방식 비교 → 조직 B, 음성, 한국어 학습, 웹 화면 → 사용자의 test 정답 검토 → 설정 고정 → 미공개 평가 시나리오와 test로 최종 평가 |
| 2026-10-15 | 음성 평가 기준 고정 → 실시간 자막으로 먼저 판단하는 정책 D → 음성 설정 고정 → 미공개 평가 시나리오를 정책 A·C·D로 음성 평가 → 디자인 하네스 → 고객사 콘솔과 관리 콘솔 |

자세한 경과와 그때그때의 판단은 [진행 기록](../PROGRESS.md)에, 중요한 결정은 [결정 기록](adr/README.md)에 있다.

## 6. 결과

결과 표와 한계는 [README](../README.md#결과-요약-2026-10-14)에 있다. 판정의 근거는 [결정 기록 0015](adr/0015-최종-평가-결과와-이후-결정.md)에 있다.

음성 결과(2026-10-15)는 채팅 결과와 따로 덧붙였다. 표는 [README의 음성 결과](../README.md#음성-결과-2026-10-15)에 있고, 판정의 근거는 [결정 기록 0020](adr/0020-음성-평가-결과와-이후-결정.md)에 있다. 음성에서는 이미 틀린 안내를 막는 것과 업무 성공이 기준을 만족했다. 근거 갱신 500ms 조건은 넘지 못했다. 음성은 말이 0.5초 멈춰야 끝난 것으로 보고, 확정 자막을 기다리는 시간도 더해지기 때문이다.
