# 0009. 업무 API는 엔진 밖의 Go 서비스로 둔다

> 처음 읽는다면: [전체 흐름 안내](../overview.md) · [용어집](../glossary.md)

- 상태: 채택
- 날짜: 2026-10-14
- 관련: `bizapi/`, `domain/org_a/api.md`, ADR 0004

## 맥락

상담 엔진은 금액과 자격을 계산하지 않고 업무 API를 부른다(ADR 0004). 실제 현장에서 업무 시스템은 엔진 바깥에 있는 별도 시스템이고, 조직마다 필드, 인증, 오류 코드가 다르다. 조직 B를 엔진 코드 수정 없이 붙이려면 엔진이 보는 계약과 조직별 구현이 분리돼 있어야 한다.

## 검토한 대안

- 엔진(Python) 안에 모의 업무 로직을 함수로 둔다: 호출 지연, 장애, 세션, 멱등성 같은 외부 시스템의 성질이 사라지고, 엔진이 업무 규칙을 직접 알게 된다.
- Python 별도 서비스: 가능하지만 엔진과 같은 코드베이스에 섞이기 쉽다.

## 결정

- 업무 API는 HTTP JSON 계약(`domain/org_a/api.md`)으로 고정하고, 조직 A 모의 서버를 Go 표준 라이브러리로 `bizapi/`에 둔다.
- 약관 규칙(견적, 이용 마지막 날, 환불 방법)은 상태 없는 패키지(`internal/orga`)에, 세션·멱등 키·접수 내역·장애 주입은 서버 패키지에 둔다.
- 조직 B는 같은 계약을 다른 어댑터로 구현한다. 엔진 쪽 차이는 설정 파일의 주소와 어댑터 이름뿐이어야 한다.

## 근거

- 모의 서버 테스트가 고객 16명의 기대 결과, 별표 2 계산 예시, 시나리오 30개의 도구 호출 기대값을 모두 통과한다(2026-10-14).
- 장애 주입(`/_admin/faults`)으로 시나리오 s19의 TIMEOUT을 재현할 수 있다.

## 예상되는 결과

- 엔진은 업무 API를 HTTP로만 부르므로, 지연과 장애가 실제 외부 시스템처럼 엔진 로그에 드러난다.
- 계약에 없던 오류 코드(`INVALID_REQUEST`, `NOT_FOUND`, `ACCOUNT_REQUIRED`, `INTERNAL`)를 계약 문서에 추가했다.
- 정해지지 않은 부분: 연 구독 중도 해지와 가족 공유 부가 상품이 함께 걸리는 환불(제18조 제3항), 이의 제기 중 결제가 있는 구독의 해지 차단 여부, 미성년자 결제의 `annual_cancel` 견적 차단 여부. 지금은 서버가 막지 않고 엔진 정책이 인계로 처리한다.
