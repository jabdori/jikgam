# 0012. 한국어 판별 모델의 기반 모델과 학습 데이터 구성

> 처음 읽는다면: [전체 흐름 안내](../overview.md) · [용어집](../glossary.md)

- 상태: 채택(val 기준. 주장 3의 판정은 `docs/evaluation.md` §8의 test 평가로 한다)
- 날짜: 2026-10-14(제안), 2026-10-14 갱신(서빙 방식·시드 변동 반영 후 채택)
- 관련: ADR 0007, ADR 0011, `docs/training.md` §10·§11, `docs/evaluation.md` §2.6, §7.2, `config/decision_models.toml`

## 맥락

주장 3(`docs/evaluation.md` §7.2)은 한국어 튜닝 모델을 같은 질문 세트의 Jev, 그리고 튜닝하지 않은 공개 판별 모델인 Clef-flash와 비교한다. 이 PC(RTX 3090 Ti)에서 서빙해 p95 200ms 이하이면서 정확도가 Jev보다 5%p 넘게 낮지 않아야 성립한다.

Unsloth는 일반 LLM에 Clef 형식 판별 헤드와 LoRA를 붙여 판별 모델로 학습하고 Jev 호환 API로 서빙하는 경로를 제공한다. 정할 것은 기반 모델의 크기와 학습 데이터 구성이다. 한국어 학습 데이터는 train 64건(판단 461개)뿐이고, 공개 영어 데이터 typed-decisions(Apache-2.0, 1,200건)가 같은 형식이다. 나중에 val 실패 유형을 기준으로 쓴 train 전용 보강 사례 104건(train_aug, 판단 777개)이 더해졌다.

## 검토한 대안

기반 모델은 Unsloth 문서가 벤치마크를 낸 Qwen3.5-0.8B와 2B. 하이퍼파라미터는 문서 권장값(4비트 LoRA r16, 학습률 2e-4, 2 에폭, 데이터가 적으면 4 에폭)으로 고정하고 데이터 구성만 바꿨다. 질문 세트는 엔진과 같은 `q-2026.10.14-mix`(ADR 0011). val 판단 152개, 보정 전 정확도(`results/training/val-screening/README.md`):

| 구성 | 0.8B | 2B |
|---|---|---|
| (a) train만 | 64.5% (98) | 71.7% (109) |
| (b) typed-decisions만 | 53.3% (81) | 55.3% (84) |
| (c) typed-decisions + train(한국어 4회 반복) | 73.7% (112) | 83.6% (127) |
| (d) typed-decisions + train + train_aug(한국어 4회 반복) | 83.6% (127) | 88.2% (134) |
| (e) train + train_aug(진단용) | 67.8% (103) | 80.3% (122) |

이 밖에 질문 세트 변경 전 문구(`q-2026.10.12`)로 학습·평가한 0.8B (a) 69.7%(106)가 있다. val을 쓴 선별 구성은 모두 11개다.

학습하지 않고 쓸 수 있는 대안은 Jev(외부 API)와 Clef-flash(Workers AI, Qwen3.5-9B 기반)다.

## 결정

- 로컬 판별 모델의 학습 데이터 구성은 (d) typed-decisions + train + train_aug이다. 한국어 사례는 4회 반복해 섞는다.
- 주장 3의 한국어 튜닝 모델은 Qwen3.5-2B (d), 시드 3407로 학습한 가중치(`weights_sha256_16` `3f9dcfe6df110822`)다. 이 PC에서 같은 프로세스 서버(`jikgam/train/serve_direct.py`, 설정 `q35-2b-ko-direct`)로 서빙한다. Studio Decision API(`q35-2b-ko`)와 가중치·답은 같고 요청 경로만 짧다.
- Qwen3.5-0.8B (d)(`q35-0.8b-ko`)는 지연 참고용으로 남긴다.
- 엔진의 기본 판별 백엔드는 ADR 0011대로 Jev다. 이 ADR은 주장 3의 비교 대상을 정한다.
- 학습 데이터의 질문 키는 실행기가 보내는 요청용 키(`applies__A-05`)로, 질문 문구는 평가와 같은 질문 세트로 만든다. Unsloth가 질문 ID를 프롬프트에 그대로 넣기 때문이다.

처음 제안(같은 날)에서는 2B의 p95가 200ms를 넘어 두 조건을 함께 만족하는 모델이 없었고, 그래서 상태를 제안으로 두었다. 서빙 방식을 바꿔 2B가 val에서 두 조건을 함께 만족한 뒤 채택으로 바꿨다(아래 "갱신").

## 근거

실행기 비교 `results/decisions/val/20261014T060432`(질문 세트 mix, 5회 반복, 서울):

| 백엔드 | 서빙 위치 | 정확도 | ECE | p50 ms | p95 ms | 요청당 USD |
|---|---|---|---|---|---|---|
| q35-0.8b-ko | 이 PC(WSL2 localhost) | 83.6% (127/152) | 0.090 | 128 | 197 | 참고 0.0000193 |
| q35-2b-ko | 이 PC(WSL2 localhost) | 88.2% (134/152) | 0.077 | 220 | 448 | 참고 0.0000358 |
| jev | TypeSafe API | 92.4% (140~141/152) | 0.147 | 182 | 242 | 0.000120 |
| clef-flash | Workers AI | 73.7% (112/152) | 0.080 | 686 | 981 | 0.000089 |

- 한국어 사례만으로는(a, e) 판단을 한쪽으로 몰아 내는 경향이 남았고(a는 sufficient 전부 true, condition_changed 전부 false), typed-decisions만으로는(b) 다수 라벨 기준선(60.5%)보다 낮았다. 둘을 섞으면 두 크기 모두 어느 한쪽만 쓸 때보다 높았다.
- (d)는 (c)보다 0.8B 15개, 2B 7개 높았고, (d)에서 typed-decisions를 뺀 (e)보다 0.8B 24개, 2B 12개 높았다.
- 2B는 Clef-flash(9B 기반)보다 22개 높고 실패 유형 태그 14개 중 13개에서 나아졌다(나머지 1개 같음). Jev보다 4.2%p 낮고, 나아진 태그는 없으며 9개에서 나빠졌다.
- 지연: 원격 호출 없이 로컬 모델만 이어서 부른 점검 실행(`20261014T060738`)에서 0.8B p95 180ms, 2B p95 348ms. 같은 프로세스 predict는 2B p95 179ms였다. 제안 당시에는 0.8B만 200ms 조건 안에 있었다(서빙 방식을 바꾼 뒤의 결과는 아래 "갱신").
- 참고 비용(§2.6)은 RunPod RTX 3090 Secure $0.50/시간으로 계산한 점유 시간 기준 값이며 외부 과금은 없다.
- 학습 비용은 작다. (d) 학습이 0.8B 13.3분, 2B 18.2분, 최대 GPU 메모리 4.4 GB 이하.

### 갱신: 서빙 방식과 시드 변동(2026-10-14)

2B 후보의 가중치는 그대로 두고 서빙 방식만 바꿔, 로컬 백엔드 하나만 부르는 실행기 실행(원격 호출 없음, 5회 반복)으로 쟀다(`docs/training.md` §10):

| 방식 | p50 ms | p95 ms | 선별 예측과 라벨 일치(판단 760개) |
|---|---|---|---|
| Studio PyTorch, 모델 하나만 | 188 | 217 | 760 |
| Studio llama.cpp GGUF BF16 / Q8_0 / Q4_K_M | 257 / 208 / 212 | 507 / 485 / 486 | 755 / 745 / 695 |
| 같은 프로세스 서버(3회) | 146 / 145 / 146 | 175 / 173 / 181 | 760 |

- llama.cpp는 회차 0에서 1.7~3.5초 걸리는 호출이 있었고, 이후 회차에서도 PyTorch보다 빠르지 않았다. 양자화하면 답이 바뀌었다.
- GPU 클럭 고정은 관리자 권한이 없어 할 수 없었다.
- Studio의 요청 경로(설정·키 확인, 별도 작업 프로세스와의 파이프)에 약 40ms가 들었다. 같은 함수(`_clef_decide`)를 서버 프로세스에서 직접 부르면 그만큼 줄고 답은 같다.

그래서 2B 후보는 val에서 §7.2의 두 조건을 함께 만족한다: 정확도는 Jev보다 4.2%p 낮고(`20261014T060432`), p95는 173~181ms다(`20261014T064204`, `20261014T064235`, `20261014T090432`).

같은 구성을 시드만 바꿔 두 번 더 학습했다(`docs/training.md` §11): 2B 134 / 128 / 126개, 0.8B 127 / 124 / 123개(시드 3407 / 3408 / 3409). 후보는 시드 3407이며 다른 시드 결과를 보고 바꾸지 않았다. 다른 두 2B 시드는 정확도 조건(이 실행 기준 133개 이상)을 만족하지 못한다.

## 예상되는 결과

- (d)의 val 수치에는 선택 효과가 섞여 있다. train_aug가 val 실패 유형을 보고 쓴 사례이고, val로 평가한 15개 구성 중 최고(시드 3개 중 최고이기도 하다)를 골랐다. test에서는 정확도 조건을 만족하지 못할 수 있다.
- 지연 조건은 로컬 백엔드만 이어서 부른 조건에서 확인했다. test의 주장 3 측정을 이 조건으로 할지는 test 평가 전에 정해 §8 절차의 ADR에 적는다. 원격 백엔드와 번갈아 부르면 Studio PyTorch에서는 꼬리가 길어졌다.
- 이 PC의 GPU 드라이버가 측정 중 Windows Update로 591.86에서 610.88로 바뀌었다. 610.88에서도 같은 프로세스 서버의 p95는 181ms였다. 610.88에서는 2B 학습이 두 번 GPU 오류로 멈췄다. test 측정 전에 드라이버를 고정하고 기록한다.
- 한국어 보강 사례를 더 쓰면 나아질 여지가 있다((c)→(d)). 보강 사례는 계속 train에만 넣고 val·test 그룹은 바꾸지 않는다.
- 서빙 응답의 모델 이름은 항상 `laya-local`이라 버전 식별에 쓸 수 없다. 설정의 가중치 해시(`weights_sha256_16`)로 식별한다.
