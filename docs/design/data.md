# 화면 수치의 정의와 출처

> 처음 읽는다면: [디자인 하네스](README.md) · [ADR 0021](../adr/0021-웹-콘솔-분리.md)

화면의 숫자는 결과 폴더의 원본 파일에서 화면을 열 때 계산한다. 손으로 적은 수치는 없다(ADR 0022 숫자 출처 검사).

모든 자료는 AI 고객과 나눈 합성 상담이며 운영 성과가 아니다. 고객사 콘솔은 메뉴 아래에 이 사실을 늘 보인다.

## 고정 값(`jikgam/web/settings.py`)

| 이름 | 값 | 뜻 |
|---|---|---|
| `CALLS_PAGE_SIZE` | 12 | 통화 기록 한 쪽의 줄 수 |
| `REPORT_PERIODS`, `DEFAULT_PERIOD` | 1·7·30·0(전체), 7 | 기간 고르기. 기준은 자료의 마지막 통화 날짜다(합성 자료라 오늘 날짜를 쓰지 않는다) |
| `REPLAY_TOP_K` | 4 | 통화 리플레이 정답 일치도의 k(ADR 0021) |
| `REPLAY_RANK_ROWS`, `REPLAY_HEAT_ROWS` | 8, 10 | 순위 막대와 순위 표의 조항 수 |
| `LIVE_START_OFFSETS`, `LIVE_LOOP_PAUSE_S`, `LIVE_REFRESH_MS` | 60·70·25초, 8초, 1,000ms | 실시간 통화 재생 피드의 시작 위치, 반복 전 쉬는 시간, 화면 갱신 간격 |
| `LOAD_CONCURRENCY`, `LOAD_DURATION_S` | 10, 300초 | 부하 벤치마크 기본값 |

## 고객사 콘솔

자료는 `config/web/tenants.toml`의 `history` 폴더(정책 C 실행)다.

- 미공개 시나리오 실행(`holdout_history`)은 `--allow-holdout`일 때만 더한다.
- 실시간 통화 재생 피드로 쓰는 기록(`live`)은 통화 기록에서 뺀다.

통화 하나는 엔진 이벤트 로그 하나다(`jikgam/web/data/calls.py`).

| 화면 값 | 정의 |
|---|---|
| 고객 이름 | `get_customer` 결과의 이름. 본인 확인 전이면 "확인 전 고객" |
| 전화번호 | `verify_identity`에 넘긴 번호의 가운데를 가린 것 |
| 문의 | 판별 응답의 요청(intent)을 처음 나온 순서로 이은 것 |
| 처리 결과 | 상담사 연결(`create_handoff` 성공 또는 마지막 정책 행동 handoff), 해지·환불 접수(`create_cancellation`·`create_refund_request` 성공), 보류(마지막 행동 hold), 중간 종료(끝난 통화의 마지막 행동이 확인 질문), 안내 완료(나머지)의 순서로 정한다 |
| 처리 결과의 세부 이름 | 접수는 해지·환불 중 무엇을 접수했는지, 안내 완료는 마지막 정책 규칙(판별 결과를 따른 안내면 마지막 요청 이름), 상담사 연결은 `create_handoff`의 사유, 보류는 마지막 정책 규칙 |
| 환불 접수액 | `create_refund_request` 결과 금액의 합 |
| 상담 시간 | 음성은 첫 고객 말 시작부터, 채팅은 첫 고객 발화부터 마지막 응답(음성은 재생 끝)까지 |
| 처리 내역 | 본인 확인(성공·실패 횟수), 구독·결제 조회(조회 도구가 성공했는지), 접수·상담사 연결, 환불(접수함, 견적이 대상 아님이면 "대상 아님", 견적 없이 해지만 했으면 "접수 안 함") |
| 안내 근거 | 고객에게 나간 답(`suggestion.exposed`)이 근거로 든 조항(처음 나온 순서). 대화 줄 아래에는 그 답의 근거를 적는다 |
| 요청이 바뀐 상담, 요청 변경 한 줄 | 시나리오가 조건 변경으로 표시한 고객 발화(`utterance.end`의 marker)가 있는 통화. 한 줄에는 그 발화 전후 판별한 요청을 적는다. 문의 열은 판별한 요청의 흐름이라 둘의 횟수가 다를 수 있다 |
| 잘못된 안내 | 평가의 무효 제안 노출(`docs/evaluation.md` §3.3)과 같은 함수(`jikgam.sim.metrics.stale_exposure`)로 센 수. 합성 상담에서는 시나리오의 표시를 쓴다. 실제 운영이라면 사람이 검토해 표시해야 한다 |
| 요약 | 생성 모델을 쓰지 않고 처리 사실로 만든다. 다른 곳에 없는 것만 적는다: 환불 접수액과 승인 대기, 견적이 대상 아님이면 그 근거 조항, 견적 없이 해지만 했으면 "환불은 접수하지 않았습니다"와 해지 접수 결과의 근거 조항, 이용 마지막 날, 상담사 연결·보류·중간 종료의 사유 |
| 대화의 가림 | 고객 발화의 전화번호 가운데, 인증을 말한 발화의 4~6자리 숫자 |

화면별로 더 쓰는 값은 아래와 같다.

| 화면 | 값 | 정의 |
|---|---|---|
| 실시간 통화 | 재생 피드 | `live`의 기록을 원래 시각대로 다시 흘린다. 지금 시각까지의 이벤트만 위 정의로 계산한다. 엔진과 외부 API를 부르지 않는다 |
| 실시간 통화 | 진행 단계 | 본인 확인 → 구독·결제 조회 → (요청) 안내 → (요청) 접수. 상담사 연결을 요청했거나 넘겨받았으면 마지막 단계가 상담사 연결이다 |
| 실시간 통화 | 고객 정보 | 조회 도구 결과의 요금제, 최근 결제, 다음 결제일, 최근 이용(ADR 0003: 시스템 기록만) |
| 실시간 통화 | 고객이 들은 길이 | 끊긴 답의 재생 기록(`tts.playback_end`의 played_ms) |
| 운영 리포트 | AI가 끝까지 처리 | (접수 + 안내 완료) ÷ 기간의 통화 수 |
| 운영 리포트 | 접수 건수 | 해지 접수 통화 수 + 환불 접수 통화 수(한 통화가 둘 다면 둘 다 센다) |
| 운영 리포트 | 평균 상담 시간, 고객 발화 평균 | 기간 통화의 상담 시간 평균, 고객 확정 발화 수 평균 |
| 운영 리포트 | 사유 막대 | 네 카드 모두 네 카드 중 가장 큰 건수를 꽉 찬 막대로 그린다. 색은 그 범주의 처리 결과 색이다 |
| 지식·정책 | 문서 | 조직 설정의 약관(`terms`)과 필수 안내 항목(`required_notices`) |
| 지식·정책 | 구간 수 | 약관 조항 수(`retrieval.parse_terms`) |
| 지식·정책 | 시행일, 판, 개정 | 약관 문서 머리말의 "시행일", "약관 버전" 줄 |
| 지식·정책 | 처리 단계 | v1에서 실제로 한 단계만 완료다. 요약은 만들지 않았다 |
| 연동 | 업무 시스템 주소 | 조직 설정 `bizapi_url` |
| 연동 | 허용 동작과 실행 조건 | 업무 API 클라이언트의 읽기·쓰기 구분(`jikgam/engine/bizapi.py`)과 엔진 정책 |
| 연동 | 목소리 | `config/voice.toml` [tts]의 목소리 이름과 언어 |
| 연동 | 상담사 연결 조건 | `tenants.toml`의 `handoff_article`이 가리키는 약관 조항의 항목 |
| 연동 | 전화번호, 데이터 보관 기간 | 설정이 없어 "정하지 않음" |

## 관리 콘솔

### 모델·벤치마크(`jikgam/web/data/benchmarks.py`)

| 값 | 정의 |
|---|---|
| 판별 모델 결과(test) | 생성형 기준선(gemini-flash)과 함께 돈 test 실행에서 백엔드마다 한 줄(`jikgam.web.dashboard.decision_runs`, `jikgam.eval.report`와 같은 계산) |
| 로컬 모델의 p95 | 그 모델만 돈 test 실행의 값(주장 3의 측정 조건, 연속 호출). 원격 백엔드와 번갈아 돈 실행의 값(간헐 호출)을 함께 적는다 |
| 판별 모델 결과(val) | 화면에서 등록한 모델이 든 val 실행의 그 모델과 기준선 |
| 사전 기준 | `docs/evaluation.md` §7.1(판별 API: 같은 실행의 gemini-flash 대비 정확도 −3%p 이상, p95 1/5 이하·500ms 이하, 비용 1/10 이하)과 §7.2(로컬 서버: Jev 대비 −5%p 이상, 혼자 서빙한 p95 200ms 이하) |
| 튜닝 모델 지연 | 연속 호출은 그 모델만 돈 test 실행의 p95, 간헐 호출은 원격 백엔드와 번갈아 돈 test 실행에서 생성형 기준선과 함께 돈 회차들의 p95 범위. 회차별 p95와 그 회차에 함께 돈 백엔드를 표로 보인다 |
| 상담 방식 결과 | 채팅 개발용 시나리오(`dev3-r*` 실행, `jikgam.web.dashboard.scenario_groups`)와 음성 미공개 시나리오(`results/voice/voice-holdout-report.json`의 집계와 사전 기준 판정, 못 미친 조건은 보고서의 판정 문구와 값을 그대로 보인다). 채팅 미공개 시나리오는 `--allow-holdout`일 때만 계산한다 |
| 부하 | `results/load/<실행>`(`jikgam.eval.load`)의 호출 수, p50·p95(성공한 호출), 오류율, 초당 호출 |
| 예상 비용 | 판별 정확도는 val 사례 수 × 반복 × 호출당 비용(최근 val 실행 세 개의 평균 토큰 × 등록 단가). 상담 시나리오는 개발용 정책 C 실행 1회분의 판별 호출 수와 다른 비용. 음성 재생은 1단계 끼어들기 재생 세션의 판별 호출 수와 STT·TTS 추정 비용 |

### 통화 리플레이(`jikgam/web/data/replay.py`)

| 값 | 정의 |
|---|---|
| 판단 | `evidence.updated` 하나. 이름은 대화 버전(v6 등) |
| 조항 순위 | 후보 조항을 적용 확률이 높은 순으로(같으면 후보 순서). 직전 판단 대비 순위 변화와 직전 확률을 함께 둔다 |
| 정답 일치 | 시나리오 파일의 정답 조항(`expected.articles`) 중 그 판단 순위 상위 k위(k=4) 안에 든 개수 |
| 순위 표의 행 | 정답 조항, 한 번이라도 선택된 조항, 확률이 높았던 조항 순으로 최대 10개 |
| 무효가 된 답 | 그 판단의 버전에서 무효가 된 제안, 재생된 길이, 끼어들기로 끊겼는지, 사유 코드 |
| 새 답 | 그 버전을 기준으로 만든 제안과 판단부터 재생 시작까지의 시간 |
| 위치 | 녹음 시작 시각(`voice.recording` 또는 `recordings.json`의 t0_ms) 기준 초 |

미공개 시나리오(h01~h20) 세션은 `--allow-holdout`일 때만 열고, 그 정답도 그때만 읽는다.

### 고객사 관리(`jikgam/web/data/tenants.py`)

| 값 | 정의 |
|---|---|
| 온보딩 | 설정 파일, 약관 문서, 업무 API 어댑터 폴더, 질문 세트 파일, 상담 기록 실행 폴더가 있는지, 계정 설정에 그 조직이 있는지 |
| 설정으로 표현한 차이 | 조직 설정의 키 가운데 고객사마다 값이 다른 것(설정 키를 함께 적는다) |
| 붙이면서 바꾼 엔진 코드 | `tenants.toml`의 `changes` 문서(`docs/org-b.md`) §5 표의 행을 분류별로 묶은 것 |
