# 평가 기준

이 저장소의 수치는 이 문서에 미리 정한 기준으로만 낸다. 결과를 보고 정의를 고르면 유리한 정의를 골랐다는 의심을 피할 수 없으므로, 기준을 두 시점으로 나눠 고정한다.

- **측정 전에 정한다(§1~§6, §8):** 2026-10-14 고정. 이 내용을 커밋한 뒤에 val 기준선을 처음 측정한다.
- **val 기준선 측정 직후, test 평가 전에 정한다(§7):** 성공 수치. 정한 날짜를 적고, test 결과를 본 뒤에는 바꾸지 않는다.

고정한 내용을 바꿔야 하면 기존 문장을 지우지 않고 변경 날짜, 이유, 바꾼 내용을 덧붙이고 ADR을 남긴다. 바꾼 뒤에는 이전 정의의 결과와 새 정의의 결과를 함께 보고한다.

## 1. 핵심 주장

프로젝트의 핵심 주장은 세 가지다. 나머지 지표는 보조 자료다.

1. 판별 모델이 생성형 LLM 판단과 비슷한 정확도를 내면서 지연과 비용을 얼마나 줄였는가
2. 고객이 조건을 바꿨을 때 근거 갱신이 얼마나 빨라졌고, 무효 제안 노출이 얼마나 줄었는가
3. 한국어 튜닝이 어떤 실패 유형을 얼마나 고쳤는가(고치지 못한 유형도 함께)

## 2. 판별 모델 평가 (주장 1, 3)

### 2.1 데이터

- `data/build/val.jsonl` 21건(판단 152개), `data/build/test.jsonl` 20건(판단 146개, sha256 앞 16자리 `5251d7d814279bf4`).
- 모델, 질문 문구, 프롬프트, 상태 구성, 임계값의 선택과 튜닝에는 val만 쓴다. test는 §8의 절차로 한 번만 평가한다.

### 2.2 입력

- 모든 백엔드는 같은 `state`와 같은 질문 정의(`data/questions.json`)를 받는다.
- 원격 백엔드에는 질문 키의 `:`를 `__`로 바꿔 보낸다(`applies:A-05` → `applies__A-05`). Workers AI가 키에 `:`를 허용하지 않아서이며, 요청 내용을 같게 두려고 모든 원격 백엔드에 똑같이 적용한다.
- 라벨 기준 문서(`docs/data-format.md`)와 필드 설명은 어떤 모델에도 주지 않는다. 생성형 LLM 프롬프트에는 작업과 출력 형식만 적는다.

### 2.3 지표

- **정확도:** 질문 유형별(intent, condition_changed, applies, sufficient, next_info, suggestion_valid, action)과 전체(판단 단위). noul은 임계값 0.5로 라벨을 정한다. 답이 없거나 호출이 실패한 판단은 오답으로 센다.
- **noul 편향 확인:** noul 질문 유형별 균형 정확도(true 재현율과 false 재현율의 평균)와 예측 true 비율. 모든 판단을 true로 내는 모델을 정확도만으로 놓치지 않기 위해서다.
- **ECE:** top-label ECE. 예측 라벨의 확률(noul은 max(p, 1−p), choice는 예측 선택지의 확률)을 [0, 1] 10개 등간격 구간으로 나누고, 구간별 |정확도 − 평균 확률|을 표본 수로 가중 평균한다. Jev의 `confidence`는 확률 분포에서 파생한 값이라 쓰지 않는다. 생성형 LLM의 확률은 모델이 출력한 수치라 판별 모델의 확률과 성격이 다르며, 비교할 때 이 차이를 함께 적는다.
- **지연:** 클라이언트에서 잰 요청 전송부터 응답 본문 수신까지의 시간. p50, p95(선형 보간). 성공한 호출만 넣고, 오류와 재시도 수는 따로 적는다.
- **비용:** 요청당 평균 USD = 입력 토큰 × 입력 단가 + 출력 토큰 × 출력 단가. 생성형 LLM의 출력 토큰에는 사고 토큰을 포함한다. 단가는 `config/decision_models.toml`에 출처와 확인 날짜를 함께 둔다.
- **상태 길이 구간별 정확도:** 내보내기 파일의 state JSON 문자 수 기준 ≤2,200 / 2,201~2,600 / >2,600. 현재 데이터의 상태는 1,102~3,821자로, 모델 입력 한도(Clef-flash 24,576 토큰, Jev 상태+가장 긴 질문 32k 토큰)보다 훨씬 짧다. 긴 상태의 영향은 엔진의 긴 통화 테스트에서 따로 본다.
- **실패 유형 태그별 정확도:** 태그가 붙은 사례의 모든 판단. 주장 3의 근거다.
- **재현성:** 같은 사례·질문에 대해 회차 간 라벨이 모두 같은 비율.

**보완(2026-10-14, val 기준선 직후):** 독립 검토자가 원본 로그를 대조하면서 문서가 정하지 않은 세부를 짚었다. 기준선 계산에 실제로 쓴 규칙을 그대로 적는다. 수치는 바뀌지 않는다.

- ECE 구간은 왼쪽 닫힘 [k/10, (k+1)/10)이고 확률 1.0은 마지막 구간에 넣는다. Jev는 확률을 소수 둘째 자리로 내서 경계값이 많으므로 이 규칙에 따라 값이 달라진다(오른쪽 닫힘이면 val 기준선 Jev 전체 ECE 0.137 → 0.141).
- choice의 예측 라벨은 확률이 가장 높은 선택지이고, 동점이면 응답의 `choice` 값을 따른다. val 기준선에서 동점은 2건이었다.
- 균형 정확도는 정답이 true와 false 둘 다 있을 때만 계산하고, 한 종류뿐이면 "정의 안 됨"으로 적는다.

### 2.4 측정 절차

`jikgam/eval/run_decisions.py`가 원본 로그를 남기고, `jikgam/eval/report.py`가 그 로그와 정답 파일만으로 표를 만든다.

- 반복: 판별 모델과 로컬 기준선 5회, 생성형 LLM 3회. 정확도는 회차별 정확도의 평균이고, 정답 수는 회차별 최소~최대로 함께 적는다.
- 순서: 회차 → 사례 → 백엔드 순으로 번갈아 호출한다. 동시 실행은 1이고, 백엔드마다 연결 하나를 유지한다.
- 예열: 측정 전에 백엔드마다 측정 데이터가 아닌 고정 요청을 한 번 보내고 기록하지 않는다. 초기 연결과 준비된 상태의 지연을 섞지 않기 위해서다.
- 재시도: HTTP 429·5xx와 연결 오류는 2, 4, 8초 뒤 최대 3번 다시 보낸다. 지연은 마지막 시도만 기록한다.
- 측정 위치: 서울. Cloudflare trace의 접속 지점과 국가, 각 API 호스트까지 TCP 연결 시간 중앙값(5회)을 측정 전후에 기록한다.
- 기록: git 커밋, 데이터 파일 sha256, 질문 세트 버전, LLM 프롬프트 버전, 백엔드 설정(단가 포함), 호출마다 응답이 알려 준 모델 버전, 요청 ID.
- 재현: 같은 원본 로그로 표를 다시 만들면 같은 표가 나와야 한다. 다시 측정하면 결정적인 모델의 정확도는 같아야 하고 지연은 네트워크에 따라 달라진다. 첫 기준선은 같은 설정으로 두 번 측정해 차이를 기록한다.
  - 보완(2026-10-14): Jev(`jev-1.13.0` 고정)는 결정적이지 않았다. val 기준선 5회 반복에서 152개 판단 중 139개의 확률이 회차마다 달랐고 9개는 라벨이 바뀌었다(모두 확률 0.45~0.56). 그래서 Jev의 정확도는 회차 평균과 최소~최대로 보고한다.
  - 보완(2026-10-14): 응답 모델은 응답 본문의 값만 기록하고, 응답에 없으면 "응답에 모델 없음"으로 남긴다. 기준선 실행의 클라이언트는 응답에 값이 없으면 설정 이름을 대신 적었으므로, 기준선 로그만으로는 응답이 버전을 알려 줬는지 증명할 수 없다. 첫 호출 확인(2026-10-14)에서는 세 API 모두 응답에 모델 값을 넣었다.

- Workers AI 모델 ID에는 버전을 고정하는 수단이 없다. 응답의 `model` 값과 측정 날짜를 기록하고, 이 한계를 결과와 함께 적는다.
- 생성형 LLM 판단은 한 사례의 모든 질문을 한 번의 호출로 묻고 JSON 스키마로 확률을 받는다. 프롬프트는 `jikgam/decision/llm.py`(버전 `llm-judge-2026.10.14`)에 고정한다. `gemini-3.8-flash`는 사고 수준 minimal을 지원하지 않아 low를 쓴다. 대형 후보였던 `gemini-4-argon`은 이 키로 호출하면 403을 반환해 제외했다(2026-10-14 확인).
- 규칙 기준선은 train과 문서만 보고 작성한다. 작성 에이전트에게 val·test와 그 내용이 담긴 파일을 열지 말라고 지시했으며, 기술적으로 막지는 않았다. 확률은 규칙별 train 정밀도다.

### 2.6 로컬 서빙 모델의 지연과 비용

튜닝한 공개 모델은 이 PC(RTX 3090 Ti)에서 Jev 호환 API로 서빙해 같은 스크립트로 잰다.

- 지연: 같은 클라이언트에서 로컬 서버까지 왕복한 시간. 원격 API와 네트워크 조건이 다르므로 표에 서빙 위치를 함께 적는다. 모델을 올리고 예열한 뒤에 잰다.
- 비용: 외부 과금은 없다. 측정 구간의 GPU 점유 시간에 같은 GPU급 클라우드 인스턴스의 시간당 단가(출처와 날짜 기록)를 곱해 요청 수로 나눈 값을 참고 비용으로 적는다. 전기료와 장비 구입비는 넣지 않는다.

## 3. 상담 엔진 지표 (주장 2)

### 3.1 엔진이 남기는 이벤트

엔진은 처음부터 다음 이벤트를 하나의 단조 시계(ms)로 기록한다. 음성의 오디오 시간축도 같은 시계에 맞춘다.

| 이벤트 | 내용 |
|---|---|
| `utterance.end` | 고객 발화 종료. 음성은 오디오상 발화 종료 시각, 채팅은 엔진이 메시지를 받은 시각 |
| `stt.partial`, `stt.final` | 미확정·확정 자막 |
| `version.bumped` | 대화 버전 증가와 원인 발화 |
| `decision.request`, `decision.response` | 백엔드, 대화 버전, 질문 ID |
| `evidence.updated` | 대화 버전, 선택한 조항 ID, 충분성, 다음 행동 |
| `suggestion.created` | 제안 ID, 기준 대화 버전 |
| `suggestion.invalidated` | 제안 ID, 무효화한 대화 버전 |
| `suggestion.exposed` | 제안 ID, 채널(콘솔·음성·채팅), 노출 시작과 끝 |
| `result.discarded` | 버전이 지나 폐기한 검색·판별·생성 결과 |
| `tool.call`, `tool.result` | 업무 API 호출과 결과 |

### 3.2 조건 변경부터 근거 갱신까지의 시간

- **조건 변경 이벤트:** 시나리오 파일의 `mid_call_events` 중 `condition_change: true`로 표시한 고객 발화(현재 8개 시나리오, 8개 이벤트), 그리고 고정 회귀 대화에서 미리 표시한 발화. 엔진 자신의 `condition_changed` 판단으로 정하지 않는다. AI 고객 테스트에서는 시뮬레이터가 이벤트를 실행한 발화를 로그에 표시한다.
- **시작(t0):** 그 발화의 `utterance.end`.
- **끝(t1):** 그 발화를 포함한 대화 버전 또는 그 이후 버전으로 계산한 `evidence.updated`가 처음 기록된 시각. 근거 집합, 충분성, 다음 행동이 새 버전 기준으로 다시 판단돼 화면과 세션 상태에 반영된 시점이다.
- **값:** t1 − t0. 미확정 자막으로 먼저 판단하는 정책에서는 음수가 나올 수 있으며 그대로 보고한다.
- **미갱신:** 다음 고객 발화나 세션 종료까지 t1이 없으면 미갱신이다. p50·p95는 미갱신을 무한대로 넣어 계산하고, 미갱신 건수를 따로 적는다.
- 정책별 p50·p95를 이벤트 수와 함께 보고한다.

### 3.3 무효 제안 노출률

- **제안:** 엔진이 만든 응답 제안(상담사 화면의 제안 문구, 자동응대가 말하거나 보낼 문구). 제안마다 기준 대화 버전이 있다.
- **노출:** 상담 콘솔에 표시되기 시작한 것(연속 표시 구간 1개를 1회로 센다), TTS 재생 시작, 채팅 전송.
- **무효 노출:** 노출 시각 이전에, 제안의 기준 버전 이후 발화 중 `invalidates_prior: true`인 조건 변경 이벤트의 t0가 있는 노출. 엔진이 그 제안을 다시 유효하다고 판단했더라도 무효로 센다. `invalidates_prior`는 "이 변경 전의 정보로 만든 처리 안내는 변경 후에 틀린다"는 뜻이며, 시나리오 파일에 미리 표시했다(현재 6개).
- **노출률:** 무효 노출 수 ÷ 같은 세션에서 `invalidates_prior: true` 이벤트의 t0 이후에 시작된 모든 노출 수.
- **이벤트 단위 보조 지표:** `invalidates_prior: true` 이벤트 중 무효 노출이 한 번이라도 있었던 이벤트의 비율.
- 채널별로 따로 보고한다. 음성은 되돌릴 수 없으므로 음성 무효 노출은 사례를 하나씩 기록한다.
- `invalidates_prior: false`인 변경(예: 시스템 기록과 다른 결제일 주장) 뒤에 다시 판단하지 않고 노출한 이전 제안은 "미재확인 노출"로 따로 세고 무효로 세지 않는다.
- `condition_change`와 `invalidates_prior` 표시는 AI가 시나리오 내용을 보고 붙인 것이다. 사람 검토 전이며, 검토 결과 바뀌면 바뀐 표시와 날짜를 기록하고 두 결과를 모두 보고한다.

### 3.4 비교할 실행 정책

| 이름 | 구성 |
|---|---|
| A. 개선형 RAG | §5.1 |
| B. 엔진 + LLM 판단 | 엔진 구조는 같고 모든 판별 질문을 `gemini-flash` 설정으로 묻는다 |
| C. 엔진 + 판별 모델, 확정 발화 | val로 고른 판별 모델. 확정 발화에서만 판단 |
| D. 엔진 + 판별 모델, 선판단 | C에 미확정 자막 선판단을 더한다(음성) |

같은 시나리오와 같은 AI 고객 설정으로 정책마다 시나리오별로 여러 번 실행한다. 반복 횟수는 엔진이 완성된 뒤 실행 비용을 보고 정하되, 결과를 보기 전에 이 문서에 적는다.

## 4. 시나리오 통과 규칙

### 4.1 판정 항목

시나리오의 `expected` 필드를 기준으로 한다.

하나라도 어기면 실패:

1. `forbidden` 항목 위반
2. 본인 확인 전 쓰기 API 호출, 또는 고객이 내용을 확인하기 전 쓰기 API 호출
3. 확정된 금액으로 안내한 환불액이 `refund_amount`와 다름
4. 쓰기 API의 핵심 인자(`customer_id`, `subscription_id`, `payment_id`, `reason`) 오류
5. 같은 대상에 접수가 두 건 이상 생김

모두 충족해야 통과:

6. 최종 행동이 `action`과 일치. `refuse`는 약관상 거절 안내와 쓰기 API 미호출, `hold`는 확답 보류 안내와 접수 미완료, `handoff`는 `create_handoff` 호출.
7. `refund_amount`가 있으면 그 금액을 안내
8. `tool_calls`의 호출이 모두 있고 핵심 인자가 맞음. 순서는 보지 않되 `verify_identity`는 쓰기 API보다 앞서야 한다. 추가 조회 호출은 허용한다.
9. `must_say` 항목을 모두 안내
10. 최종 안내의 근거 조항에 `articles`가 모두 포함됨. 추가 조항은 실패가 아니며 근거 정밀도로 따로 보고한다.

보조 지표(통과 판정에 쓰지 않음): intent 일치, 근거 정밀도, 대화 턴 수, 불필요한 확인 질문 수.

### 4.2 판정 주체

- **코드:** 2, 4, 5, 8, 10, 그리고 6의 도구 호출 부분. 3과 7은 엔진이 구조화 필드로 남긴 안내 금액으로 판정한다. 엔진은 금액을 안내할 때 확정 여부와 금액을 구조화해 기록한다.
- **AI 평가:** 1 중 코드로 볼 수 없는 것, 6의 안내 내용, 9. 평가 모델과 프롬프트는 엔진 설정을 고정하기 전에 고정하고, 응답 생성 모델과 다른 모델을 쓴다.
- **사람:** AI 평가 판정 중 무작위로 고른 10건 이상을 확인하고 일치율을 보고한다.
- **고객 AI 지시 준수:** 고객 AI가 `reveal_rules`와 `mid_call_events`를 지켰는지 따로 판정한다. 지키지 않은 실행은 무효로 하고 그 수를 보고한다.
- 같은 시나리오를 여러 번 돌려 통과율을 분포로 보고한다.

### 4.3 개발용과 보류용 시나리오

- `data/scenarios/org_a.jsonl`의 30개는 엔진 개발에 쓴다. 이 결과는 "개발용 시나리오 결과"로만 표기한다.
- 최종 주장에 쓸 보류용 시나리오는 엔진 개발에 참여하지 않는 별도 작성자가 같은 형식으로 쓰고, 엔진 설정을 고정하기 전에 커밋한다. 엔진 개발자는 이 파일을 읽지 않으며, 설정 고정 후 한 번 평가한다. test 분할과 마찬가지로 열람 금지는 지시로만 지킨다.

## 5. 시스템 기준선 정의

### 5.1 개선형 RAG

- 문서 처리와 검색은 엔진과 같다. 조항 단위 색인, 조항 ID와 구조 보존, 하이브리드 검색(키워드 + 임베딩), 구조 확장(참조, 예외, 부칙, 별표).
- 판별 계층, 대화 버전, 무효화가 없다. 고객의 확정 발화마다 대화 전체와 검색 결과로 생성형 LLM을 한 번 호출해 답한다. 업무 API는 LLM의 도구 호출로 쓴다. 진행 중인 생성은 새 발화가 와도 취소하지 않는다.
- 생성 모델은 엔진의 응답 생성 모델과 같다.

### 5.2 값싼 규칙 기준선

판별 평가의 `rules`(§2.5)와 같다.

## 6. 보고 규칙

- 비율은 건수와 함께 쓴다. 예: "판단 152개 중 131개".
- 합성 데이터와 AI 고객 결과를 실제 운영 성과로 표현하지 않는다.
- 개선되지 않은 항목도 함께 보고한다.
- 모든 수치는 원본 로그 경로와 함께 기록한다. README와 진행 기록에 들어가는 수치는 그 수치를 만든 작업과 분리된 검토자가 원본 로그와 대조한 뒤에 쓴다.

## 7. 성공 수치

2026-10-14에 val 기준선(`results/decisions/val/20261014T020803`, 질문 세트 `q-2026.10.12`)을 본 직후, 질문 문구나 프롬프트를 바꾸는 실험을 하기 전에 정했다. test 결과를 본 뒤에는 바꾸지 않는다. 판정은 §8의 test 평가 한 번으로 하며, 조건 일부만 만족하면 만족한 것과 못한 것을 그대로 보고한다.

### 7.1 주장 1: 판별 모델 대 생성형 LLM

test에서 val로 고른 판별 모델(설정은 §8에서 ADR로 고정)과 `gemini-flash`를 같은 질문 세트로 비교한다. 세 조건을 모두 만족하면 성립으로 본다.

- 정확도: 판별 모델이 `gemini-flash`보다 3%p 넘게 낮지 않다(판단 146개에서 약 4개). val에서 Jev는 1.3%p 낮았다.
- 지연: 판별 모델의 p95가 `gemini-flash` p95의 1/5 이하이고 500ms 이하다.
- 비용: 판별 모델의 요청당 비용이 `gemini-flash`의 1/10 이하다.

### 7.2 주장 3: 한국어 튜닝

비교 대상은 같은 질문 세트의 Jev와, 한국어 튜닝을 하지 않은 공개 판별 모델인 `clef-flash`다.

- 정확도: 튜닝 모델이 Jev보다 5%p 넘게 낮지 않다.
- 지연: 이 PC(RTX 3090 Ti)에서 서빙한 튜닝 모델의 p95가 200ms 이하다(동시 실행 1, 예열 후).
- 실패 유형 태그별로 `clef-flash`와 Jev 대비 나아진 태그와 나빠진 태그를 모두 보고한다. 이 항목은 성립 판정에 쓰지 않는다.

### 7.3 주장 2: 근거 갱신과 무효 제안 노출

아직 엔진 기준선이 없으므로 같은 원칙으로 시점을 정한다. 개발용 시나리오로 정책 A~D를 처음 측정한 직후, 보류용 시나리오를 평가하기 전에 이 절에 수치를 적고 날짜를 남긴다.

## 8. test 평가 절차

1. 모델(버전 ID), 질문 세트 버전, 프롬프트, 상태 구성, 임계값을 고정하고 그 내용을 ADR로 남긴다.
2. 사용자가 test 20건의 대화, 정답, 이유를 직접 검토한다. 검토한 사례는 `source`를 `reviewed`로 바꾼다. 정답을 고쳐야 하면 test를 수정하지 않고 진행 기록에 남긴다.
3. 고정한 설정으로 test를 한 번 평가한다. 결과를 본 뒤에는 §7과 설정을 바꾸지 않는다.
