# 조직 B 붙이기: 설정과 어댑터만으로 되는가

`docs/design.md` §11의 원칙 "조직별 차이는 설정과 어댑터로만 표현한다"를 검증한 기록이다. 가상 조직 B(책솔, 전자책·오디오북 구독)를 같은 상담 엔진에 붙이고, 엔진에서 바꿔야 했던 것을 모두 적는다. 작업일 2026-10-14.

## 1. 결론

- 조직 B는 **설정 파일 하나**(`config/orgs/org_b.toml`), **조직 B용 질문 세트 하나**(`data/question_sets/q-2026.10.14-mix-orgb.json`), **업무 API 어댑터**(`bizapi/internal/orgbgw`)로 붙었다. 엔진은 조직 B 업무 시스템을 모르고 어댑터의 공통 계약만 부른다.
- 엔진 코드는 **두 가지**(파일 세 개)를 바꿨다(§5). 하나는 조직 A 규칙이 엔진 코드에 박혀 있던 것을 설정으로 옮긴 **일반화**(중복 결제 후보 판단의 "같은 날" 기준), 하나는 조직과 무관한 **버그**(문장 끝 마침표 앞의 인증번호를 읽지 못함)다. 둘 다 조직 A 동작을 바꾸지 않는다.
- `jikgam/decision/`, `jikgam/baselines/`, `jikgam/sim/`과 조직 A 파일(설정, 약관, 고객 데이터, 질문 세트, 재생 파일, `bizapi/internal/orga`·`server`)은 바꾸지 않았다.
- 그래서 "엔진 코드를 바꾸지 않는다"는 목표는 **이번에는 달성하지 못했다**. 다만 바꾼 것은 설정 키 하나를 더한 것과 정규식 한 줄이고, 조직 A 가정이 남아 있는 곳은 §6에 적었다.

## 3. 무엇이 설정이고 무엇이 어댑터인가

**설정(`config/orgs/org_b.toml`)으로 표현한 것:** 약관 경로, 기준일(2026-10-13), 어댑터 주소, 판별 백엔드(jev), 질문 세트, 임계값(조직 A와 같은 값), 필수 안내 4개, 검색의 요청별 낱말·구어 확장 21개·절차 조항 규칙(조직 B 조항 ID), 요청별 견적 사유(셋뿐), 견적 우선순위, 환불·해지 사유 집합, 승인 안내·조항, 제3자 거절 조항(B-14, B-12: 가족 이용권 구성원도 제3자), 법정대리인 사유 없음, 청약철회 기간 14일, 주장 패턴, 장애 보상 규칙(귀책 company·vendor, 2시간, 2배), 중복 결제 후보 간격 27일(새 키, §5).

**새 질문 세트(설정이 가리키는 데이터):** 조직 A의 `q-2026.10.14-mix` 선택지 문구 4곳에 조직 A 약관 내용이 있었다(부가 상품, 월·연 구독·무료 체험, 이용 이력, 미성년자·본인 확인 2회). 조직 A 파일을 고치지 않고 그 4곳만 바꾼 `q-2026.10.14-mix-orgb`를 만들었다. 질문 ID·유형·선택지 라벨은 같다(`tests/test_questions.py`, `tests/test_org_b.py`). 조직 B 판별 데이터가 없어 이 문구로 val 정확도를 잰 적이 없다. 엔진 전용 질문(`engine-extra.json`)은 조직 중립이라 그대로 쓴다.

**어댑터(`bizapi/internal/orgbgw`)로 흡수한 것:** 경로·메서드, 시스템 키, 회원 토큰 보관(세션별), 멱등 키 위치, 필드 이름(`member_no→customer_id`, `pass_no→subscription_id`, `charge_no→payment_id` 등), 값(`YEARLY→annual`, `PHONE→mobile`, `OURS/VENDOR→company/vendor`, `minutes/60→hours`, `+09:00` 시각 → KST 날짜), 환불 유형 ↔ 공통 사유(`COOLING_OFF↔withdrawal`, `YEARLY_PRORATE↔annual_cancel`, `DOUBLE_CHARGE↔duplicate`), 상담사 연결 코드 → 인계 사유(`CHARGEBACK→dispute`, `REPEAT_REFUND→repeat_refund`), 응답 봉투, 오류 코드 13개 → 공통 오류 코드, 조직 B에 없는 공통 사유(`incident`, `minor`, `trial_cancel`, `plan_change`)는 업무 시스템을 부르지 않고 `NOT_ELIGIBLE`, 장애 주입 전달. 전체 표는 `domain/org_b/api.md` §2.

**조직 B 업무 시스템(`bizapi/internal/orgb`, `orgbsrv`)이 하는 것:** 금액과 자격 판단 전부(14일 청약철회, 일할 계산, 같은 이용 기간 중복, 이의 제기·환불 반복 연결, 30,000원 승인, 환불 경로, 해지 후 마지막 날, 가족 구성원 종료). 엔진과 어댑터는 계산하지 않는다(ADR 0004).

## 4. 어댑터를 어디에 두었나

조직 B 업무 시스템 앞에 Go 게이트웨이를 두었다(`go run ./cmd/orgbgw`, 127.0.0.1:8098 → 조직 B 127.0.0.1:8097). 엔진 설정의 `bizapi_url`만 어댑터를 가리킨다.

- **ADR 0009를 따른다.** 업무 API는 엔진 밖 HTTP 서비스이고 "조직 B는 같은 계약을 다른 어댑터로 구현한다. 엔진 쪽 차이는 설정 파일의 주소와 어댑터 이름뿐이어야 한다." 엔진의 업무 API 클라이언트(`jikgam/engine/bizapi.py`)는 그대로다.
- **엔진(Python) 안 어댑터를 쓰지 않은 이유:** 조직별 필드·인증·오류 코드 분기가 엔진 코드에 들어가고, 조직을 늘릴 때마다 엔진을 고쳐야 한다. 엔진 쪽 클라이언트 인터페이스를 조직별로 갈라야 해서 이번 검증의 기준("엔진 코드를 바꾸지 않는다")을 처음부터 어기게 된다.
- **조직 B 업무 시스템 안에 공통 계약을 넣지 않은 이유:** 실제 현장에서는 조직의 업무 시스템을 바꿀 수 없다. 조직 B 모의 서버는 자기 계약만 갖게 하고 변환은 어댑터에만 두었다.
- **게이트웨이의 성질:** 인증 판단은 하지 않는다(토큰을 붙여 보내고 조직 B의 `AUTH_REQUIRED`를 `IDENTITY_REQUIRED`로 바꾼다). 재시도하지 않는다(재시도 예산은 엔진이 공통 코드로 쓴다). 장애 주입도 조직 B로 넘겨, 재생 파일의 `faults`가 조직 B 오류 → 어댑터 변환 → 엔진 재시도 예산 경로를 탄다(`tests/test_org_b.py::test_engine_retry_budget_sees_translated_timeout`). 상태는 세션별 회원 토큰과 시도 수뿐이며 메모리에 둔다.
- **대가:** 호출마다 HTTP 한 단계가 더 생긴다. 이번 재생에서 어댑터를 거친 조회·견적·쓰기 호출은 8~112 ms였다(같은 PC, 엔진 로그 `tool.result`의 `latency_ms`). 조직 A 모의 서버 직접 호출과 같은 조건의 비교는 하지 않았다.

테스트: `bizapi/internal/orgb/rules_test.go`(회원별 `_case` 11명, 별표 2 예시), `orgbsrv/server_test.go`(조직 B 계약: 시스템 키, 3회 잠금, 토큰, 멱등 키 헤더, 오류 코드, 장애 주입), `orgbgw/gateway_test.go`(필드·값 변환, 토큰과 멱등 키, 오류 코드 변환표 전체, 장애 전달, 초기화, 연결 실패·시간 초과·형식 오류), `tests/test_org_b.py`(설정 정합성, 엔진 클라이언트가 바뀌지 않은 채 어댑터와 동작, 가짜 판별·생성으로 돌린 엔진 세션).

조직 A 동작을 바꾸지 않았다는 근거:

- `uv run pytest` 338개 통과(변경 전 326개 + 새 테스트 12개), `cd bizapi && go test ./...` 통과.
- 1번: 기본값 0에서 새 조건은 이전 조건과 논리적으로 같다. 조직 A 설정 파일에 키가 없음을 테스트로 고정했다(`test_org_a_config_has_no_duplicate_window_key`).
- 3번: 바꾸기 전후 정규식을 조직 A 개발용 재생 18개, 개발용 시나리오, train·val·사례 파일의 모든 문자열 29,650개에 돌렸다(보류용 자료는 열지 않았다). 차이는 3개였고 모두 학습 데이터의 같은 발화("네, 사칠이… 공일구요. 472019.")다. 이 발화는 읽어 둔 소리 숫자와 같은 값을 한 번 더 읽는 것이라 정책이 쓰는 마지막 인증번호는 같다. 재생 파일에는 차이가 없다. AI 고객 시뮬레이터가 쓴 고객 발화(엔진 로그의 `utterance.end`)도 소리 숫자 변환 뒤 같은 비교를 했다: 메인 작업 폴더의 로그 773개(이 브랜치에 있는 461개를 포함하고, 진행 중인 정책 비교 측정도 포함, 읽기만 함)에서 차이 0개. 그래도 측정 중에는 엔진 코드를 고정하는 것이 원칙이므로, 이 브랜치는 정책 비교 측정이 끝난 뒤 합치는 것이 안전하다.
- 조직 A 재생 s01·s07·s08(같은 날 중복과 소리 인증번호가 있는 재생)을 바꾼 엔진으로 다시 돌려 이전 실행(`results/engine/dev/20261014T065502-C`, `20261014T063615-C`)과 비교했다: 도구 호출(턴, 도구, 인자, 결과 코드), 고른 견적, 제안 규칙이 모두 같다(`results/engine/org_b/20261014-orga-regress`). 생성 문장은 LLM이라 비교하지 않았다.

`jikgam/decision/`, `jikgam/baselines/`, `jikgam/sim/`: 변경 없음. 조직 A 파일: 변경 없음.

## 6. 바꾸지 않았지만 조직 A 가정이 남아 있는 곳

이번 조직 B 재생에는 영향이 없었지만, 다른 조직이면 엔진 변경이 필요할 수 있는 곳이다.

1. **견적 사유의 어휘와 의미가 엔진 코드에 있다.** `policy._plausible`이 `withdrawal`, `incident`, `annual_cancel`, `duplicate`, `minor`, `trial_cancel`, `plan_change`의 뜻과 요금제 값 `annual`·`monthly`를 직접 안다. 모르는 사유는 항상 "물어볼 만하지 않음"이다. 조직 B는 어댑터가 자기 환불 유형 셋을 이 어휘로 바꿔 문제가 없었지만, 이 어휘에 없는 사유(예: 월 이용권 해지 일할 환불)가 있는 조직은 설정만으로 견적을 묻게 할 수 없다. 공통 계약 문서(`domain/org_a/api.md`)에도 요금제 값은 적혀 있지 않다.
2. **`window_days` 하나가 청약철회와 장애 환불에 함께 쓰인다.** 두 기간이 다른 조직은 표현할 수 없다(조직 B는 장애 환불이 없어 문제 없음).
3. **`policy.current_payment`는 가장 최근 결제를 현재 이용 기간의 결제로 본다.** 조직 B처럼 다른 날 중복 결제가 있으면 기간 시작이 하루 늦게 잡힌다(M1006: 10-02가 아니라 10-03). 청약철회 후보 필터와 장애 기록 조회 구간(`incident_window`)에 쓰인다. 자격은 업무 시스템이 다시 판단하므로 이번 결과는 같았다.
4. **`duplicate_window_days=27`의 한계.** 몇 달 간격인 연 이용권 중복 결제는 이 필터로 잡지 못하고, 고객이 "두 번" 결제됐다고 말할 때만 묻는다.
5. **`minor_age`는 필수 키다.** 조직 B에서는 쓰이지 않는데 값을 넣어야 한다.
6. **생성 프롬프트(`generate.SYSTEM_PROMPT`)**는 조직 중립이지만 일부 설명이 조직 A 맥락이다(법정대리인 = 미성년 회원, 차감액 = 연 구독 결제 금액 등). 조직 B 재생에서 문제는 없었다.
7. **엔진 전용 질문(`engine-extra.json`)** 중 `caller`의 "만 19세 미만", `addon_only`의 "가족 공유"가 조직 A 문구다. 조직 B는 부가 상품이 없어 `addon_only`를 묻지 않는다.
8. **AI 고객 시뮬레이터(`jikgam/sim/customer.py`)의 시스템 프롬프트가 "별담 플러스"를 고정한다.** 조직 B 시나리오를 시뮬레이터로 돌리려면 바꿔야 한다(이번에는 고정 재생만 썼다).
9. **규칙 판별 기준선(`jikgam/decision/rules.py`)**은 조직 A 조항 ID와 요금을 상수로 갖는다. 조직 B 판별 백엔드로 쓸 수 없다(조직 B 설정은 jev).
10. **정책 A 기준선(`jikgam/baselines/rag.py`)**의 함수 설명에 조직 A 사유 설명(연 구독 중도 해지, 월→연 차감 등)이 있다. 조직 B를 정책 A로 돌리지 않았다.
11. **생성 검사의 환불 주장 오탐.** 1차 실행 b05에서 "전체 해지 및 환불을 진행하시려면 관리 회원 본인께서 직접 문의"를 환불 주장으로 보아 한 번 다시 만들었다(`generate._REFUND_CLAIM`의 "진행하"). 조직과 무관하다.
12. **어댑터의 회원 토큰은 메모리에만 있다.** 어댑터가 다시 시작되면 엔진의 쓰기는 `IDENTITY_REQUIRED`가 되고 엔진은 본인 확인을 다시 묻는다. 토큰 만료는 흉내 내지 않았다.
13. **조직 B 질문 세트와 임계값은 val로 잰 적이 없다.** 조직 B 판별 데이터가 없다.
