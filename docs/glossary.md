# 용어집

이 문서는 저장소의 문서와 코드에 나오는 내부 용어를 쉬운 말로 풀어 둔 목록이다. 다른 문서를 읽다가 낯선 낱말이 나오면 여기서 찾으면 된다. 전체 흐름은 [전체 흐름 안내](overview.md)에 있다.

## 모델과 판단

| 용어 | 뜻 |
|---|---|
| 판별 모델(decision model) | 문장을 쓰지 않고 정해진 형식의 질문에 확률로만 답하는 모델. "예/아니오"나 "이 중 하나"를 고른다. 빠르고 싸다. [설계 문서](design.md)에서는 System One 방식이라고도 부른다. |
| 생성형 LLM | 문장을 써서 답하는 큰 언어 모델. 이 저장소에서는 Gemini(`gemini-3.8-flash`, `gemini-3.1-pro-preview`)를 썼다. |
| Jev | TypeSafe의 판별 모델. 버전을 `jev-1.13.0`으로 고정해 썼다. 엔진의 기본 판별 모델이다. |
| Clef, Clef-flash | Cloudflare의 공개 가중치 판별 모델. Jev와 같은 요청 형식을 쓰고 Cloudflare Workers AI에서 호출했다. |
| 학습한 2B, 튜닝 모델 | Qwen3.5-2B에 한국어 상담 판단을 학습시킨 판별 모델. 설정 이름은 `q35-2b-ko-direct`다. |
| 백엔드 | 판단을 실제로 수행하는 모델이나 서비스. 엔진은 백엔드 이름만 알고 설정으로 바꿔 끼운다. |
| 질문 세트 | 판별 모델에 던지는 질문 문구 묶음(`data/questions.json`, `data/question_sets/`). 최종 평가에는 `q-2026.10.14-mix`를 썼다. |
| noul | 예/아니오 질문 유형. 판별 모델이 "예"일 확률을 낸다. 0.5 이상이면 예로 본다. |
| choice | 여러 선택지 중 하나를 고르는 질문 유형. |
| 상태(state) | 판별 모델에 주는 입력. 대화, 그때까지 확인된 사실(`known_facts`), 후보 약관 조항을 묶은 것이다. |
| 규칙 기준선, 다수 라벨 기준선 | 비교용 단순 방법. 사람이 짠 규칙과, 가장 흔한 정답만 고르는 방법이다. |

## 판별 질문

| 질문 ID | 묻는 것 |
|---|---|
| `intent` | 고객이 지금 원하는 처리(환불, 해지, 해지+환불 등) |
| `condition_changed` | 마지막 발화가 이미 기록된 사실이나 요청을 바꾸거나 정정했는가 |
| `applies:<조항ID>` | 그 조항이 지금 처리에 필요한 근거인가(예: `applies:A-05`) |
| `sufficient` | 후보 조항과 확인된 사실만으로 처리 결과를 확정할 수 있는가 |
| `next_info` | 다음에 고객에게 확인할 정보(본인 확인, 계좌 등) |
| `action` | 다음 행동: 안내(answer), 질문(ask), 상담사 연결(handoff), 보류(hold) |
| `suggestion_valid` | 전에 만든 응답 제안이 지금도 맞는가 |

## 상담 엔진

| 용어 | 뜻 |
|---|---|
| 상담 엔진 | 고객 발화를 받아 검색, 판별, 정책 판단, 응답 생성을 하는 프로그램(`jikgam/engine/`). |
| 대화 버전 | 판단 결과를 바꿀 수 있는 입력이 들어올 때마다 1씩 오르는 번호. 고객의 확정 발화, 시스템 사실을 바꾸는 업무 시스템 조회 결과가 여기에 해당한다. 옛 버전 기준으로 진행 중이던 작업은 취소하거나 결과를 버린다. 쓰기 API 호출은 취소하지 않는다. |
| 근거 조항 | 안내의 바탕이 되는 약관 조항. 조항 ID는 `A-05`(조직 A의 제5조), `T-01`(조직 A의 별표 1), `B-05`, `BT-01`(조직 B)처럼 쓴다. |
| 근거 갱신 | 대화가 바뀐 뒤 필요한 근거 조항, 충분성, 다음 행동을 새 버전 기준으로 다시 판단해 화면에 반영하는 것. |
| 제안(suggestion) | 엔진이 만든 응답 문안. 상담사 화면에 보이거나 고객에게 나간다. 어느 대화 버전으로 만들었는지(기준 버전)를 함께 기록한다. |
| 노출 | 제안이 상담사 화면에 뜨거나, 채팅으로 보내지거나, 음성으로 재생되기 시작한 것. |
| 정책 코드 | 본인 확인 우선, 인계 사유, 업무 시스템 장애 시 보류처럼 정해진 규칙을 판별 모델 대신 처리하는 코드(`jikgam/engine/policy.py`). |
| 업무 시스템, 업무 API | 고객 조회, 환불 금액 계산(`quote_refund`), 해지·환불 접수, 상담사 연결을 하는 외부 시스템. 여기서는 Go로 만든 모의 서버(`bizapi/`)다. |
| 고객 진술, 시스템 기록 | 고객이 말로만 한 사실과 업무 시스템에서 조회한 사실. 둘이 다르면 시스템 기록을 따른다(결정 기록 0003). |
| 인계(handoff) | 약관상 상담사가 처리해야 해서 상담사에게 넘기는 것. |
| 보류(hold) | 근거가 없거나 시스템 장애로 확답하지 않고 미루는 것. |
| 조직(org) | 가상의 회사. `org_a`(구독 서비스 "별담 플러스")와 `org_b`(전자책·오디오북 구독 "책솔")가 있다. |
| 어댑터 | 회사마다 다른 업무 시스템의 형식(필드, 인증, 오류 코드)을 엔진이 쓰는 공통 형식으로 바꿔 주는 변환 장치. |

## 음성

| 용어 | 뜻 |
|---|---|
| STT, TTS | 음성 인식(말 → 글)과 음성 합성(글 → 말). Gemini 3.5 Transcribe Live와 Gemini TTS를 썼다. |
| 미확정 자막(partial), 실시간 자막 | 음성 인식이 말하는 도중에 내는 임시 자막. 말이 끝나면 확정 자막(final)이 온다. |
| 선판단 | 정책 D에서, 고객이 말하는 도중 실시간 자막이 바뀔 때마다 첫 판별을 미리 돌려 두는 것. 세션 상태는 바꾸지 않고, 나중에 같은 입력으로 판단할 때만 그 결과를 쓴다. |
| 잠정 확정 | 정책 D에서, VAD가 말 끝을 판정하면 확정 자막을 기다리지 않고 마지막 실시간 자막을 확정 발화로 엔진에 넘기는 것. 확정 자막이 다르면 그 자막을 새 발화로 넘겨 다시 판단한다. |
| VERBATIM 모드 | 음성 인식이 들은 그대로 받아 적는 모드. "똑똑한" 모드(SMART)는 고객의 정정 발화를 지워서 쓰지 않는다. |
| 끼어들기(barge-in) | 엔진의 음성 응답이 재생되는 중에 고객이 말을 시작하는 것. 재생을 멈춘다. |
| Pipecat | 음성 파이프라인을 만드는 오픈소스 런타임. |
| VAD | 말소리의 시작과 끝을 잡는 장치. 이 저장소에서는 말이 0.5초 멈추면 끝으로 판정한다. |

## 평가와 측정

| 용어 | 뜻 |
|---|---|
| train, val, test | 판별 데이터의 세 묶음. train은 연습(학습)용, val은 모델과 문구를 고르는 조정용, test는 최종 시험용이다. test는 나눈 뒤 바꾸지 않고 설정을 고정한 뒤 한 번만 쓴다. |
| 판단 | 사례 하나에 딸린 질문 하나. test 사례 20건에는 판단 146개가 있다. |
| 시나리오 | AI 고객이 연기할 상담 상황. 고객의 목표, 아는 사실, 말투, 도중의 정정과 기대하는 결과를 적었다. |
| 개발용 시나리오 | 엔진을 만들고 고치는 데 쓴 시나리오 30개(`data/scenarios/org_a.jsonl`). |
| 미공개 평가 시나리오(보류용 시나리오) | 엔진 개발에 참여하지 않은 작성자가 쓰고 개발 중에는 아무도 열어 보지 않은 최종 평가용 시나리오 20개(`data/scenarios/org_a_holdout.jsonl`). 문서에서는 "보류용 시나리오"라고도 부른다. |
| 정책 A, B, C | 비교한 세 상담 방식. A는 개선형 RAG 챗봇, B는 같은 엔진 + 생성형 LLM 판단, C는 같은 엔진 + 판별 모델(Jev)이다. 정책 D는 음성에서 실시간 자막으로 먼저 판단하는 방식이다(결정 기록 0018, 결과는 0020). |
| 개선형 RAG(정책 A) | 검색은 엔진과 같지만 판별 모델, 대화 버전, 작업 취소가 없는 비교 기준. 고객의 확정 발화마다 대화 전체와 검색 결과로 생성형 LLM을 한 번 부른다(평가 기준 문서 5.1절). |
| RAG | 질문에 맞는 문서를 검색해 생성형 LLM에 함께 넣고 답을 만드는 구조. |
| 조건 변경부터 근거 갱신까지의 시간 | 고객이 조건을 바꾸는 말을 끝낸 시점부터 엔진이 새 버전 기준으로 근거를 다시 판단해 반영한 시점까지의 시간. 대표 지표다. |
| 무효 제안 노출(이미 틀린 안내) | 고객이 조건을 바꾼 뒤에도, 바꾸기 전 정보로 만든 제안이 노출된 경우. 대표 지표다. |
| 빠른 정정 | 시나리오 실행 방식의 하나. 조건을 바꾸는 말을 직전 고객 메시지 1,000ms 뒤에, 엔진 응답을 기다리지 않고 보낸다. 실제 채팅에서 연달아 보내는 경우와 음성의 끼어들기를 흉내 낸 것이다. |
| 판정 항목 1~10 | 시나리오 통과 규칙(평가 기준 문서 4.1절). 금지 행동, 본인 확인 전 접수, 금액, 도구 호출, 필수 안내 등을 본다. |
| 10번 항목(근거 조항) | 판정 항목 중 "안내에 쓴 근거 조항에 시나리오가 기대한 조항이 모두 들어 있는가". |
| 고객 AI, 판정기 | 시나리오대로 고객을 연기하는 AI(`gemini-3.8-flash`)와, 코드로 볼 수 없는 판정 항목을 채점하는 다른 AI(`gemini-3.1-pro-preview`). |
| 무효 실행 | 판정에서 뺀 시나리오 실행. 기준은 고객 AI가 시나리오 지시(정보 공개 규칙, 도중의 사건)를 지켰는지다. 최종 평가에서는 실행기와 판정기의 문제로 무효가 된 실행도 있었다(결정 기록 0015). |
| 회차 | 같은 설정으로 반복한 실행 한 번. 결과의 흔들림을 보려고 여러 번 돌린다. |
| p50, p95 | 지연 시간 분포의 중앙값과 95번째 백분위수. p95는 요청 100개 중 느린 쪽 5개를 뺀 나머지 중 가장 느린 값에 가깝다. |
| ECE | 확률이 실제 정답률과 얼마나 맞는지 보는 보정 오차. 작을수록 확률을 믿을 만하다. |
| 부트스트랩 구간 | 데이터를 다시 뽑아 결과를 여러 번 계산해 얻은 불확실성의 범위. 대화 단위로 다시 뽑았다. |
| 설정 고정(freeze) | 최종 평가 직전에 코드, 설정, 데이터의 해시를 결정 기록에 적어 바꾸지 않기로 한 것(결정 기록 0014). |
| 독립 검토 | 수치를 만든 작업과 분리된 검토자가 원본 로그로 다시 계산해 대조하는 것. |
| typed-decisions | Hugging Face의 공개 영어 판별 데이터셋(`LocalLLaMA/typed-decisions`). 한국어 학습 때 섞어 썼다. |
| Unsloth | 일반 LLM에 판별 헤드와 LoRA를 붙여 판별 모델로 학습하고 Jev와 같은 형식의 API로 서빙하는 도구. |
| 보강 사례(train_aug) | val에서 드러난 실패 유형을 보고 새로 쓴 train 전용 사례 104건. val과 test에는 넣지 않았다. |

## 웹 화면

| 용어 | 뜻 |
|---|---|
| 고객사 콘솔 | 상담 운영팀이 매일 쓰는 웹 화면(`/app/`). 실시간 통화, 통화 기록, 운영 리포트, 지식·정책, 연동. 엔진 용어와 수치를 넣지 않는다(결정 기록 0021). |
| 관리 콘솔 | 직감 팀 내부용 웹 화면(`/admin/`). 모델·벤치마크, 통화 리플레이, 고객사 관리. 어두운 테마에 ADMIN 표시를 단다. |
| 디자인 하네스 | 화면의 일관성과 불필요한 요소를 사람 눈이 아니라 검사로 잡는 장치. 토큰 린트, 고객사 화면 금지어, 숫자 출처, 스크린샷, 접근성, 독립 리뷰로 이루어진다(결정 기록 0022). |
| 토큰 | 색, 글꼴, 크기, 간격, 모서리 값을 한 파일(`jikgam/web/static/tokens.css`)에 이름 붙여 둔 것. 화면 코드는 이름만 쓴다. |
| 재생 피드 | 실시간 통화 화면이 기록된 합성 통화를 원래 시각대로 다시 흘려 보여 주는 것. 엔진과 외부 API를 부르지 않는다. |
| 통화 리플레이 | 음성 통화의 녹음을 재생하면서 판단마다 조항 순위, 무효가 된 답, 새 답을 따라가는 관리 콘솔 화면. |
| 정답 일치도 | 통화 리플레이에서 시나리오 정답 조항 중 그 판단 순위 상위 4위 안에 든 개수. |

## 문서 표기

| 표기 | 뜻 |
|---|---|
| ADR, 결정 기록 | 되돌리기 어렵거나 결과에 영향을 주는 결정을 하나씩 적은 문서(`docs/adr/`). 결정이 바뀌면 고치지 않고 새 ADR을 쓴다. |
| §, 예: §7.3 | 절 번호. `docs/evaluation.md` §7.3은 [평가 기준 문서](evaluation.md)의 7.3절이다. 문서 이름 없이 쓰면 그 문서 자신의 절이거나, 결정 기록과 진행 기록에서는 대개 평가 기준 문서의 절이다. |
| 보완(날짜) | 고정 문서를 고치지 않고 날짜와 이유를 붙여 덧붙인 내용. |
| 합성 데이터 | AI가 만든 가상의 대화와 사례. 실제 운영 데이터가 아니다. |
