# 설계 문서

> 이 문서는 풀려는 문제, 핵심 가설, 시스템 설계와 실험 원칙을 다룬다. 프로젝트가 왜 이런 구조인지 알고 싶은 사람이 README 다음에 읽으면 된다.
> 구현 세부는 [엔진 설계](engine.md), 측정 정의는 [평가 기준](evaluation.md), 낯선 낱말은 [용어집](glossary.md)에 있다.

## 1. 문제

상담 중에는 고객의 말이 계속 바뀐다. 처음에는 해지를 말하다가 환불로 바뀌고, 결제일을 잘못 말했다가 정정하고, 사용한 적이 있는지를 뒤늦게 말한다. 그때마다 적용되는 약관 조항과 올바른 안내가 달라진다.

일반적인 RAG 챗봇은 질문 하나에 검색 한 번, 생성 한 번을 한다. 이 구조로는 두 가지가 어렵다.

- **대화가 바뀔 때마다 근거를 다시 판단하기.** 매 발화마다 생성형 LLM을 호출하면 느리고 비싸다. 그래서 판단을 덜 자주 하게 되고, 그 사이 상담사에게는 이미 틀린 제안이 남아 있다.
- **여러 조항을 함께 봐야 하는 질문.** 일반 규정, 예외 조항, 부칙, 별표가 함께 적용되는 질문에서 오류가 많다. 이전에 폐쇄망 환경에서 사내 규정 RAG를 검증하면서 문서 분할 방식을 바꿔 환각을 줄였지만, 남은 오류는 대부분 이런 다중 근거 질문이었다.

## 2. 가설

빠르고 저렴한 판별 모델(System One 방식: 상태와 타입이 정해진 질문을 받아 확률로 답하는 모델)에 작은 판단을 맡기면, 판단을 훨씬 자주 할 수 있다. 그러면 다음이 가능해진다.

- 고객 조건이 바뀌는 즉시 근거를 갱신하고, 이전 제안을 무효화한다.
- 생성형 LLM은 근거가 충분하다고 판단된 순간에만 호출한다.
- 근거가 부족하면 답하지 않고 확인 질문이나 보류로 간다.

검증할 지표는 다음 두 가지를 중심으로 한다.

- 의미 있는 조건 변경부터 근거 갱신까지 걸린 시간 (p50, p95)
- 이미 무효가 된 제안이 화면이나 음성으로 노출된 비율

## 3. 범위

- 실시간 음성·채팅 입력과 대화 상태 관리
- 판별과 생성을 분리한 상담 엔진
- 외부 판별 API(Jev)와 공개 가중치 판별 모델의 비교
- 한국어 상담 판단에 맞춘 판별 모델 추가 학습
- 여러 조항을 함께 쓰는 근거 선택
- 업무 API 연동(조회, 해지·환불 접수, 상담사 인계)
- AI 음성 고객을 이용한 종단 간 자동 테스트
- 조직별 정책과 연동을 설정으로 분리
- 상담 콘솔, 턴 상세 타임라인, 평가 대시보드 웹 화면

## 4. 제공 모드

같은 상담 엔진을 세 가지 방식으로 쓴다.

- **상담사 보조:** 실시간 자막, 확인된 고객 조건과 미확인 조건, 근거 조항과 판별 확률, 응답 제안, 무효화 표시, 인계 버튼.
- **음성 자동응대:** 엔진의 답변을 TTS로 전달하고, 정정·끼어들기·확인 질문·보류·인계를 처리한다.
- **검증·비교:** 고정 대화와 녹음 재생, 반응형 AI 고객, 모델별 비교, 단계별 지연·비용·오류 관찰, 실패 사례 회귀 테스트.

## 5. 시스템 설계

### 5.1 문서 처리와 검색

- 제목·절·조항 구조를 보존하고 조항 ID를 붙인다.
- 의미 단위로 나누고, 조각마다 요약과 핵심 키워드를 붙인다.
- 조항 간 참조(관련 조항, 예외, 부칙, 별표)와 부모 문맥을 연결한다.
- 조직, 상품, 버전, 시행일, 계약 적용 시점 메타데이터를 둔다.
- 문서 처리와 인덱싱은 사전 처리로 분리한다.

### 5.2 입력 통합

- 음성은 스트리밍 STT로 바꾸고, 미확정 자막과 확정 발화를 구분한다.
- 채팅도 같은 대화 이벤트 형식으로 들어온다.
- 미확정 발화는 선판단·선검색에 쓸 수 있지만, 모든 중간 자막마다 전체 검색과 생성을 돌리지 않는다.

### 5.3 대화 상태

현재 문의 목적, 구독·결제 정보, 확인된 조건과 미확인 조건, 고객의 정정, 선택된 근거, 대화 버전을 유지한다. 고객이 말하지 않은 사실을 모델이 임의로 확정하지 않는다. 고객 진술과 시스템 조회 결과는 구분해서 기록한다.

### 5.4 판별 계층

판별 모델이 맡는 의미 판단은 다음과 같다.

- 의도와 조건 변경 감지
- 후보 조항이 지금 필요한 근거인지
- 근거 집합이 처리 결과를 확정하기에 충분한지
- 다음에 확보할 정보
- 이전 응답 제안의 유효성
- 다음 행동(답변, 질문, 인계, 보류)

날짜 비교, 권한 확인, 금액 계산처럼 결정적인 일은 코드로 처리한다. 판별 모델은 금액을 계산하지 않고, 업무 API가 계산한 금액과 근거 조항을 안내한다.

Jev는 하나의 상태에 여러 질문을 병렬로, 서로 독립적으로 평가한다. 질문을 늘려도 지연이 거의 늘지 않는 대신, 질문끼리 서로를 보지 못한다. 그래서 "이 조항들을 함께 보면 충분한가"는 개별 질문의 합으로 나오지 않으며, 선택한 근거 집합을 상태에 넣고 별도 질문으로 묻는다.

### 5.5 다중 근거 선택

1. **후보 확장(코드):** 하이브리드 검색 결과에 문서 구조로 연결된 부모 절, 참조 조항, 예외, 부칙, 별표를 붙인다.
2. **판단 축별 평가(판별 모델):** 문의 유형별로 필요한 판단 축을 설정에 두고, 후보 조항마다 필요한 근거인지를 한 요청에서 병렬로 묻는다.
3. **집합 선택(코드):** 판단 축을 덮는 조항을 고르고 중복을 줄인다.
4. **충분성 판단(판별 모델):** 선택한 근거와 확인된 사실을 하나의 상태로 묶어 처리 결과를 확정할 수 있는지 묻는다. 부족하면 생성 대신 확인 질문이나 보류로 간다.

필요한 조항이 검색 후보에 아예 없으면 순서를 바꿔도 해결되지 않는다. 이 경우는 평가 데이터에 따로 두고, 충분성 판단이 이를 잡아내는지 본다.

### 5.6 응답 생성

생성형 LLM은 선정된 근거와 확인된 사실만 받아 답변을 만든다. 근거 연결, 미확인 사실 명시, 확인 질문, 필수 안내를 포함한다. 고객 조건이 바뀌면 진행 중인 검색·생성을 취소하거나 결과를 폐기한다. 이미 말한 음성은 되돌릴 수 없으므로, 금액 확답과 접수는 고객 확인을 거친다.

### 5.7 업무 API

조회, 환불 견적, 해지·환불 접수, 계좌 등록, 상담사 인계로 구성한다. 계약은 `domain/org_a/api.md`에 있다. 쓰기 작업은 본인 확인과 고객 확인 이후에만 하고, 모두 멱등 키를 받는다.

### 5.8 운영 안정성과 관측

- 대화·요청 버전 관리, 취소, 오래된 결과 폐기
- 타임아웃과 재시도 예산
- 모델·검색 장애 시 대체 경로(근거 표시, 확인 질문, 보류)
- 세션과 조직 간 데이터 분리
- 근거 ID, 모델 버전, 요청 조건 기록
- 단계별 지연과 비용 추적

## 6. 판별 모델과 한국어 학습

Jev는 영어가 주 학습 언어이며, 한국어를 포함한 다른 언어는 처리하지만 성능이 같지 않다고 공식 문서에 적혀 있다. 고객별 파인튜닝은 제공하지 않는다.

- **Jev:** 외부 API 기준선.
- **공개 판별 모델:** Unsloth의 decision model 학습 경로로 공개 LLM(Qwen, Gemma 등)에 판별 헤드와 LoRA를 붙여 만든다.
- **한국어 튜닝 모델:** 한국어 상담 판단의 실패 유형으로 추가 학습한 결과물.

학습 목적은 한국어 답변 생성이 아니라 한국어 상담에서의 판단이다. 부정·정정, 생략, 구어체와 약관 문어체의 차이, 숫자·날짜, STT 오류, 유사 조항, 근거 부족을 다룬다. 약관 내용은 외우게 하지 않고, 입력된 근거를 해석하는 능력을 학습한다.

원칙은 다음과 같다.

- 학습·검증·테스트를 대화 단위로 분리한다.
- 확률 보정과 임계값은 검증 데이터로만 정한다.
- 테스트는 모델, 질문 문구, 임계값을 고정한 뒤 평가한다.
- 개선되지 않은 항목도 보고한다.
- Jev 출력을 학습 데이터로 쓰는 것은 이용 약관 확인 후 결정하며, 쓰더라도 유일한 정답 출처로 두지 않는다.

파인튜닝은 추론을 빠르게 하지 않는다. 속도는 모델 크기, 입력 길이, 양자화, 하드웨어, 서빙 구조가 정한다. 파인튜닝은 정해진 지연과 비용 안에서 필요한 정확도를 확보하는 수단이다.

API 형식이 호환되어도 동작은 다를 수 있다. Unsloth로 서빙한 모델은 질문을 한 프롬프트에서 함께 판단하고 입력 길이 한도도 다르므로, 질문 수와 상태 길이별 결과를 따로 보고한다.

## 7. 폐쇄망 배포

외부 API를 쓸 수 없는 환경에서는 로컬 판별 모델을 쓴다. 다만 판별 모델만 로컬이라고 전체가 폐쇄망 대응인 것은 아니다. 임베딩, 검색 저장소, 생성형 LLM, STT, TTS, 로그, 모델 업데이트 경로를 각각 구분해서, 실제로 지원하는 범위만 밝힌다.

## 8. AI 음성 고객 테스트

AI 고객에게는 상황, 목표, 알고 있는 사실, 질문받을 때만 공개할 정보, 말투, 정정·끼어들기 조건을 준다. 기대 정답과 근거 조항은 보여주지 않는다.

고객 AI의 음성은 실제 STT 경로를 통과해야 한다. 텍스트를 바로 넣은 결과로 음성 시스템을 검증했다고 하지 않는다.

- **고정 회귀:** 같은 대화·녹음 재생, 수정 전후 비교.
- **반응형 대화:** 조건 변경, 정정, 모호한 표현, 다중 턴.
- **음성·장애:** 잡음, 겹치는 발화, 끼어들기, STT 오인식, 지연, API 실패, 문서 누락·상충, 잘못된 약관 버전.

평가는 역할을 나눈다. 코드는 필수 질문, 조항 ID, 도구 호출 인자, 금지 동작, 오래된 결과 사용을 검사한다. AI 평가는 자연스러움과 근거·답변의 일치를 본다. 사람은 정답 기준과 중요한 정책 위반을 검토한다. 고객 AI가 지시대로 행동했는지도 따로 확인하고, 같은 시나리오를 여러 번 돌려 성공률을 분포로 보고한다.

## 9. 비교 실험

비교 대상은 개선형 RAG 기준선, 생성형 LLM 판단(대형·경량), Jev, 튜닝 전 공개 판별 모델, 한국어 튜닝 모델이다.

- **모델 비교:** 같은 판별 데이터(`data/`)로 모델만 바꾼다. 정확도, 보정 오차, p50/p95 지연, 요청당 비용을 상태 길이 구간별로 본다.
- **시스템 비교:** 판별 모델을 고정하고 실행 정책만 바꾼다. 확정 발화에서만 판단, 미확정 자막에서도 선판단, 모든 판단을 생성형 LLM에 맡김.

측정 항목은 다음과 같다.

- **근거:** 필요한 조항의 검색 여부, 다중 근거 충족률, 예외 조항 누락
- **판별:** 조건 변경 감지, 적용 판단, 정보 부족 처리, 잘못된 확신
- **응답:** 근거 없는 주장, 잘못된 정책 적용, 필수 안내 누락, 불필요한 거절. 모든 질문을 거절하는 시스템이 유리해지지 않도록 처리율과 업무 성공률을 함께 본다.
- **반응성:** 조건 변경부터 근거 갱신까지, 발화 종료부터 제안·첫 음성까지, 무효 결과 노출
- **비용:** 세션당 호출 수, 생성형 LLM 사용량, API 비용, 로컬 서빙 비용
- **업무:** 조회·접수 정확성, 도구 인자, 중복 방지, 장애 복구, 인계

실험 원칙은 다음과 같다.

- 모델 버전, 입력 길이, 하드웨어, 동시 실행 수를 기록한다. 외부 API는 버전 ID를 고정한다.
- 초기 로딩과 준비된 상태의 지연을 구분한다.
- 외부 API 지연은 실제 사용 지역(서울)의 네트워크 조건에서 측정하고 그 조건을 밝힌다.
- 성능 목표는 기준선 측정 후 정하고, 테스트 결과를 보고 바꾸지 않는다.
- 합성 상담 결과를 실제 운영 성과로 표현하지 않는다.

## 10. 재사용하는 오픈소스와 직접 만드는 것

재사용 후보는 음성 런타임(LiveKit Agents 또는 Pipecat 중 하나), 판별 모델 학습·서빙(Unsloth), 사용자 시뮬레이션(Scenario 또는 런타임의 테스트 기능), 키워드·벡터 검색, 웹 프레임워크, 트레이싱 도구다. 한국어 STT·TTS 지원과 유지보수성을 확인해 하나씩 고른다.

직접 만드는 것은 업무 모델링, 조항 구조화, 대화 상태와 정정 처리, 검색·판별·생성의 실행 조건, 다중 근거 선택, 한국어 데이터와 학습, 업무 API 연동, 조직별 설정, 평가 기준과 실패 분석이다.

## 11. 조직별 설정

같은 엔진에 가상 조직 A와 B를 붙인다. 차이는 설정과 어댑터로만 표현한다.

- 약관 묶음과 버전·시행일
- 문의 유형별 필수 판단 축
- 필수 안내 문구
- 업무 API 어댑터(필드, 인증, 오류 코드)
- 승인 단계와 기준 금액
- 모델 라우팅과 대체 경로

목표는 조직 B를 붙일 때 엔진 코드를 바꾸지 않는 것이다. 무엇이 공통이고 무엇이 조직별인지를 이 과정에서 기록한다.
