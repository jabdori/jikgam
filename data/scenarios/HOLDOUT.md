# 보류용 평가 시나리오

`org_a_holdout.jsonl`은 엔진 설정을 고정한 뒤 핵심 주장(특히 주장 2, `docs/evaluation.md` §3.2·§3.3)과 시나리오 통과율(§4)을 한 번 평가하는 데 쓰는 보류용 시나리오다(§4.3). 개발용 `org_a.jsonl`과 형식이 같다.

## 작성 규칙

- 엔진 개발에 참여하지 않은 별도 작성자(독립 작성 에이전트)가 썼다. 작성자는 `CLAUDE.md`, `docs/evaluation.md`, `docs/design.md`, `docs/data-format.md`, `domain/org_a/terms.md`(r2), `domain/org_a/api.md`, `bizapi/`, 개발용 고객·시나리오 파일의 형식만 보았고, 엔진 코드(`jikgam/engine/`, `jikgam/baselines/`), 조직 설정(`config/orgs/`), 재생 대화·결과(`data/replays/`, `results/`), 판별 데이터(`data/build/`, `data/cases*`), `PROGRESS.md`는 열지 않았다. 엔진을 통과시키거나 떨어뜨리려 하지 않고 약관이 정하는 현실적인 상황을 썼다.
- 엔진 개발자는 엔진 설정을 고정하기 전에 다음 파일을 읽지 않는다. 열람 금지는 test 분할과 마찬가지로 지시로만 지킨다.
  - `data/scenarios/org_a_holdout.jsonl`
  - `domain/org_a/customers_holdout.json`
  - `bizapi/internal/orga/holdout_test.go`, `bizapi/internal/server/holdout_test.go`(기대 결과가 들어 있다)
- 설정 고정 후 한 번만 평가한다. 평가 뒤에는 이 파일들을 고치지 않고, 문제가 있으면 진행 기록에 남긴다.
- 모든 고객·대화는 가상이다. 실제 약관 문구나 개인정보를 쓰지 않았다.

## 실행

보류용 고객(C201~C220)과 장애 기록 1건은 `customers_holdout.json`에 있고, 업무 API를 두 파일로 띄운다.

```sh
cd bizapi
go run ./cmd/bizapi -addr 127.0.0.1:8095 -data ../domain/org_a/customers.json -data ../domain/org_a/customers_holdout.json
```

`mid_call_events`의 `inject`는 개발용 s19와 같은 형식이며 `/_admin/faults`로 주입한다.

## 구성

| 항목 | 수 |
|---|---|
| 시나리오 | 20 (h01~h20) |
| 보류용 고객 | 20 (C201~C220), 개발용 고객 사용 0 |
| `condition_change: true` 이벤트가 있는 시나리오 | 9 (이벤트 10개) |
| 그중 `invalidates_prior: true` 이벤트가 있는 시나리오 | 7 (이벤트 8개) |
| `inject`(업무 API 장애 주입)가 있는 시나리오 | 2 (일시 장애 후 재시도 성공 1, 지속 장애 1) |
| 제3자 통화자 또는 통화 중 화자 교체가 있는 시나리오 | 3 |
| 기대 행동 | answer 14, handoff 3, refuse 2, hold 1 |
| 기대 환불액이 있는 시나리오 | 13 (그중 상담사 승인 대상 5) |

인계 시나리오는 제19조 제1항의 세 사유(미성년자 결제 취소, 이의 제기, 본인 확인 2회 실패)를 하나씩 다룬다. 고객 기억과 시스템 기록이 다른 경우, 생략·지시어, 구어체·STT 오인식 표현이 여러 시나리오에 섞여 있다.

`condition_change`와 `invalidates_prior`는 작성자가 붙였다(사람 검토 전). 무효화 이벤트는 고객이 접수에 동의하기 전에 일어나도록 이벤트 문구에 시점을 적었다. 빠른 정정(§3.3 보완)으로 보내도 쓰기 API와 경합하지 않게 하기 위해서다.

## 기대값 검증

- 모든 환불액, 승인 여부, 환불 방법, 이용 가능 마지막 날은 손계산이 아니라 모의 업무 API(`quote_refund`, `create_cancellation`)로 냈다.
- `bizapi/internal/orga/holdout_test.go`: 보류용 고객 20명의 `_case` 메모를 `quote_refund`·해지 규칙으로 표 테스트한다. 같은 파일의 `TestMergeKeepsDevQuotes`는 두 파일을 합쳐 읽어도 개발용 고객의 모든 견적(고객 × 구독 × 사유)이 바뀌지 않는지 확인한다. 장애 기록이 전역이어서다.
- `bizapi/internal/server/holdout_test.go`: 20개 시나리오의 `expected.tool_calls`를 두 파일로 띄운 서버에 순서대로 재생해, 모든 호출이 받아들여지고(주입한 장애는 그 횟수만큼 해당 오류), 환불액·승인 상태·이용 마지막 날·해지 구독이 기대와 같고 같은 결제에 접수가 두 건 생기지 않는지 확인한다.
- 형식: 모든 줄이 개발용 파일과 같은 키 집합·순서(최상위, `caller`, `persona`, `expected`, `mid_call_events`)인지 확인했다.
- 블라인드 재도출: 시드 20261012로 무작위로 고른 5개(25%)와 작성자가 고른 복잡한 3개를, `terms.md`와 해당 고객 기록·상황만 받은 별도 에이전트가 기대값을 보지 않고 다시 도출해 비교했다. 결과는 아래에 적는다.

블라인드 재도출 결과(2026-10-14): 8개 모두 최종 행동, 환불액, 승인 여부, 환불 방법, 이용 마지막 날, 해야 할 쓰기 호출과 하지 말아야 할 쓰기 호출이 기대값과 같았다. 차이는 재도출 쪽이 근거 조항을 더 넓게 든 것뿐이었다(추가 조항은 §4.1에서 실패가 아니다). 비교 뒤 한 시나리오의 `outcome` 설명에 필수가 아닌 참고 문장을 하나 더했고, 작성자 검토에서 한 시나리오의 `articles`에서 결과에 필요하지 않은 조항 하나를 뺐다. 금액·행동·도구 호출은 바뀌지 않았다.

검증 중 확인한 약관·API의 해석 여지(시나리오는 이 지점에 기대값이 걸리지 않게 썼다):

- 중복 결제를 약관은 "같은 이용 기간"으로 정하지만 API는 같은 날 결제만 묶는다.
- `quote_refund`의 `minor`는 기준일 현재 결제 한 건만 본다. 미성년자 때 한 이전 결제는 견적으로 확인할 수 없다.
- 부가 상품만 청약철회하는 경우 제5조와 제18조 제2항이 부딪친다. API는 제18조 제2항을 따른다. 이용 이력은 구독별이 아니라 고객별이다.
- 연 구독은 이용을 유지하면서 자동 갱신만 멈추는 방법이 약관·API에 없다(제4조 제3항과 제8조 제4항).
- 연 구독 중도 해지 시 함께 해지되는 부가 상품의 환불(제18조 제3항)을 API는 계산하지 않는다.
- 청약철회가 자동 갱신 해지까지 포함하는지 제5조에 명시가 없다(개발용 시나리오와 같이 해지 접수를 함께 기대했다).
- 제13조 제2항의 법정대리인 관계 서류가 성인이 된 회원 본인의 요청에도 필요한지 불분명하다.
- 50,000원 초과 환불의 승인(제19조 제2항)과 환불 소요 기간(제14조)의 기산점 관계가 정해져 있지 않다.
- 등록한 환불 계좌를 고칠 API가 없다(다시 등록하면 `DUPLICATE_REQUEST`).
- 장애 기록이 전역이라 데이터 파일을 더하면 기존 고객의 판단이 바뀔 수 있다. 이번 병합에서는 바뀌지 않음을 테스트로 확인했다.
